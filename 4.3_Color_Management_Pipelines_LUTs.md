# 4.3 Color Management Pipelines & LUTs

## Theory: CMS Architectures and OCIO

### Color Management System (CMS) Fundamentals

**Purpose:** Systematic approach to maintaining color accuracy and consistency across devices, software, and workflows

**Core CMS Components:**

```
1. Color Space Definitions:
   - Primary chromaticities (x, y for R, G, B)
   - White point (x, y coordinates)
   - Transfer function (gamma, log, PQ, HLG)
   - Bit depth and data range (legal/float)

2. Transform Library:
   - IDTs (camera → working space)
   - ODTs (working space → display)
   - Look transforms (creative grades)
   - Utility transforms (saturation, contrast)

3. Configuration:
   - Rules for automatic transform selection
   - Color space roles (input, working, display)
   - Transform chains and dependencies

4. Display Calibration:
   - Hardware calibration (probe + software)
   - Profile generation (ICC, EDID)
   - Verification (patches, measurements)

5. Policy Enforcement:
   - Required color spaces for specific tasks
   - Bit depth requirements
   - Viewing condition standards
```

**CMS Implementation Approaches:**

```
Proprietary (Vendor-Specific):
- DaVinci Resolve RCM
- Adobe Color (Premiere, After Effects)
- Avid Color Management
- Pros: Tight integration, optimized performance
- Cons: Vendor lock-in, limited interoperability

Open Standards:
- ACES (Academy Color Encoding System)
- OCIO (OpenColorIO)
- ICC (International Color Consortium)
- Pros: Interoperable, future-proof, industry standard
- Cons: Complex setup, requires expertise

Hybrid:
- ACES within vendor system
- OCIO configs for software integration
- Pros: Best of both worlds
- Cons: Configuration complexity
```

### OCIO (OpenColorIO) Architecture

**Core Concepts:**

```
OCIO Configuration Structure:

1. Roles:
   - Color spaces with specific purposes in pipeline
   - Examples: scene_linear, srgb_texture, rec709_display

2. Color Spaces:
   - Defined by primaries, transfer function, reference space
   - Can be scene-referred or display-referred
   - Hierarchical (inherit from parent)

3. Displays:
   - Available output devices (monitors, projectors)
   - Each has associated view transform

4. Views:
   - Rendering intents for each display
   - Examples: Scene-Referred, Display-Referred, Film Look

5. Looks:
   - Optional color modifications (creative grades)
   - Can be chained in sequence

6. Policies:
   - Rules for automatic color space selection
   - File name patterns, environment variables
```

**OCIO Configuration File (config.ocio):**

```
ocio_profile_version: 2

environment:
  {
    OCIO: "ocio://" # Current config path
  }

search_path: "Luts:ColorSpaces"

roles:
  color_picking: "acescg"
  color_timing: "acescg"
  compositing_log: "log"
  data: "scene_linear"
  default: "acescg"
  reference: "ACES2065-1"
  scene_linear: "scene_linear"
  texture_paint: "srgb_texture"

colorspaces:
  - !<ColorSpace>
    name: "ACES2065-1"
    family: "ACES"
    equalitygroup: ""
    bitdepth: 32f
    description: |
      ACES Scene-Referred Working Space
    isdata: true

  - !<ColorSpace>
    name: "Rec.709"
    family: "Display"
    equalitygroup: ""
    bitdepth: 10i
    description: |
      Rec.709 Display (Gamma 2.4)
    from_reference: !<GroupTransform>
      children:
        - !<FileTransform>
          src: "Rec709_to_rec709_gamma24.spi1d"
          interpolation: linear

  - !<ColorSpace>
    name: "srgb_texture"
    family: "Texture"
    equalitygroup: ""
    bitdepth: 8i
    description: |
      sRGB gamma for textures (assets)
    allocationvars: [0, 1]
    from_reference: !<GroupTransform>
      children:
        - !<FileTransform>
          src: "linear_to_srgb.spi1d"
          interpolation: linear

displays:
  sRGB: {Rec.709: {view: false}, ACES: {view: true}}
  DCI-P3: {Rec.709: {view: false}}

views:
  ACES:
    - !<View>
      name: "ACES RRT+ODT"
      colorspace: "Rec.709"

active_displays: [sRGB, DCI-P3]
active_views: [ACES]

file_rules:
  - !<Rule>
    name: "Default Rule"
    colorspace: "Rec.709"
    regex: ".*"
```

**OCIO Transform Types:**

```
1. FileTransform (LUT application):
   !<FileTransform>
     src: "logc4_to_709.cube"
     interpolation: tetrahedral

2. MatrixTransform (3×3 or 4×4 matrix):
   !<MatrixTransform>
     src: "AWG_to_Rec709.mat"

3. ColorSpaceTransform (internal):
   !<ColorSpaceTransform>
     src: "LogC4"
     dst: "Rec709"

4. GroupTransform (chain):
   !<GroupTransform>
     children:
       - !<FileTransform> ...
       - !<MatrixTransform> ...

5. LookTransform (OCIO looks):
   !<LookTransform>
     name: "teal_and_orange"
     direction: forward
```

### ACES Architecture with LUTs

**ACES Pipeline Components:**

```
1. Input (Capture Side):
   Camera RAW → IDT (Input Device Transform)

2. Processing (Working Space):
   IDT Output → ACES2065-1 (Scene-Linear)
              → ACEScg (Working Space for VFX/Grading)

3. Look Modification (Optional):
   ACEScg → LMT (Look Modification Transform)

4. Output (Display Side):
   ACES/LMT → RRT (Reference Rendering Transform)
           → ODT (Output Device Transform)
           → Display (Rec.709, P3, HDR)

Full Pipeline:
Camera → IDT → ACES2065-1 → [LMT] → RRT+ODT → Display
```

**IDT (Input Device Transform) Creation:**

```
IDT converts camera-specific values to ACES2065-1:

For ARRI Alexa (LogC4):

def logc4_idt(CV_log, metadata):
    # Convert 10-bit LogC4 code values to linear
    linear = logc4_to_linear(CV_log / 1023.0)

    # Apply white balance correction
    WB_matrix = metadata['wb_gains']
    linear_wb = apply_matrix(linear, WB_matrix)

    # Convert ARRI Wide Gamut 4 to ACES2065-1
    # Primary chromaticities matrix transform
    AWG4_to_ACES = [[... 3×3 matrix ...]]
    aces = matrix_multiply(linear_wb, AWG4_to_ACES)

    # Scale to ACES 1.0 exposure
    aces = aces * (1.0 / 0.18)  # Middle gray normalization

    return aces

Result: Scene-linear ACES values suitable for:
- VFX compositing
- Color grading
- Cross-camera compatibility
```

**ODT (Output Device Transform) Creation:**

```
ODT converts ACES to display-specific values:

For Rec.709 (100 nits):

def aces_to_rec709_odt(ACES_color):
    # Apply RRT (Reference Rendering Transform)
    # Tone mapping, gamut mapping
    RRT_out = RRT(ACES_color)

    # Apply ODT specific to Rec.709
    # Target: 100 nits, gamma 2.4, Rec.709 primaries

    # Tone map highlights to 100 nit range
    ODT_mapped = tone_map(RRT_out, 100.0)

    # Convert ACES primaries to Rec.709 primaries
    ACES_to_Rec709 = [[... 3×3 matrix ...]]
    rec709_linear = matrix_multiply(ODT_mapped, ACES_to_Rec709)

    # Apply Rec.709 gamma 2.4
    rec709_gamma = rec709_linear^(1/2.4)

    # Scale to 10-bit code values
    CV_10bit = round(rec709_gamma * 1023)

    return CV_10bit

Common ODTs:
- Rec.709 (100 nits, broadcast)
- DCI-P3 (48 nits, cinema)
- P3-D65 (for mastering)
- Rec.2020 + PQ (1000 nits HDR)
- Rec.2020 + HLG (1000 nits HDR)
```

### LUT Integration in CMS

**Transform Chain Management:**

```
Typical Transform Chain:

1. Input Transform (Technical):
   Camera Log → Scene-Linear Working Space
   Method: IDT LUT or matrix transform

2. Look Transform (Creative):
   Scene-Linear → Scene-Linear with look
   Method: Creative LUT, CDL, or plugin

3. Output Transform (Technical):
   Working Space → Display Space
   Method: ODT LUT or combined transform

Example Chain (ARRI → Rec.709 with look):
LogC4 (AWG4) → [IDT] → ACES2065-1 → [Show Look LMT] →
ACES2065-1 → [RRT+ODT for Rec.709] → Rec.709 (100 nits)

LUTs in chain:
- IDT: 1D or matrix (usually not full 3D LUT)
- LMT: 3D LUT for creative look
- RRT+ODT: 1D+3D LUT combined (shaper + CLUT)
```

**OCIO Display Pipeline:**

```
Viewer Transform Selection:

1. Determine source color space:
   - From file metadata
   - From project settings
   - From OCIO role (compositing_log, etc.)

2. Determine display and view:
   - User selects display (sRGB, P3, HDR)
   - User selects view (Scene-Referred, Film Look)

3. Build transform chain:
   Source → Working Space → Look → Display

4. Apply transform to viewer:
   - Real-time GPU processing
   - Optional cache for performance
   - Scope display affected by transform

Example:
Source: LogC4 footage
Working: ACEScg
Look: "Teal and Orange"
Display: Rec.709

Transform:
LogC4 → IDT → ACEScg → Look LUT → ODT → Rec.709
```

## Practice: OCIO Config and ACES LUT Generation

### OCIO Config Setup

**Basic OCIO Configuration:**

```
Project Setup Steps:

1. Download OCIO:
   git clone https://github.com/AcademySoftwareFoundation/OpenColorIO
   Build and install OCIO libraries

2. Create project config:
   - Copy example config.ocio
   - Modify for project color spaces
   - Define custom LUT locations

3. Integrate with software:
   - Nuke: Built-in OCIO support
   - Resolve: OCIO config in project settings
   - Maya/Houdini: Environment variables

4. Verify setup:
   - Test with known color spaces
   - Check transform accuracy
   - Validate with test patterns
```

**Custom Color Space Definition:**

```
Adding Custom Camera Color Space:

# In config.ocio colorspaces section:

- !<ColorSpace>
  name: "Sony_SLog3_SGamut3"
  family: "Camera"
  equalitygroup: "Sony"
  bitdepth: 10i
  description: |
    Sony Venice S-Log3 with SGamut3 color
  isdata: false

  from_reference: !<GroupTransform>
    children:
      # Convert ACES2065-1 to SGamut3
      - !<MatrixTransform>
        src: "ACES_to_SGamut3.mat"

      # Apply S-Log3 transfer function
      - !<FileTransform>
        src: "linear_to_slog3.spi1d"
        interpolation: linear

# Usage in software:
# File → OCIO → Color Space → Sony_SLog3_SGamut3
```

### ACES LUT Generation

**Generating RRT+ODT LUTs:**

```
Method 1: ACES CTL Transform

1. Download ACES transforms:
   git clone https://github.com/ampas/aces-dev

2. Locate CTL files:
   - transforms/ctl/rrt.ctl (Reference Rendering Transform)
   - transforms/ctl/odt.ctl (Output Device Transform)

3. Use OCIO tool (ocioconvert) to generate LUT:
   ocioconvert --input-space "ACES2065-1" \
              --output "Rec709.100nits.ctl" \
              --format "Cube" \
              --size 33 \
              aces_idt.ctl

Method 2: Manufacturer LUTs

1. Download camera manufacturer LUTs:
   - ARRI: LUT package from ARRI website
   - Sony: Venice LUT package
   - RED: IPP2 LUT package

2. Convert to ACES IDT format:
   - Use manufacturer IDT generator tools
   - Or reverse-engineer from existing LUTs
   - Validate with test charts

3. Test in ACES pipeline:
   - Apply IDT to camera footage
   - Check against reference
   - Verify ACES2065-1 output
```

**ACES Look Creation Workflow:**

```
Creating ACES-Compatible Show Look:

1. Grade in ACES environment:
   - Use Resolve or Baselight with ACES mode
   - Timeline color space: ACEScg
   - Display: Rec.709 ODT

2. Create LUT from grade:
   - Export grade as LUT (resolve allows this)
   - Extract 3D LUT from node tree
   - Or export as CDL + LUT combination

3. Format as LMT:
   - Convert LUT to OCIO format
   - Add to OCIO config as "look"
   - Test on ACES footage

4. Document:
   - Show look parameters
   - Application instructions
   - Known limitations

Result:
Reusable show look compatible with any ACES footage
```

### Software-Specific Integration

**DaVinci Resolve RCM vs. OCIO:**

```
Resolve Color Management (RCM):
- Built-in color management
- Simpler setup than OCIO
- Optimized for Resolve performance
- Limited to Resolve ecosystem

OCIO in Resolve:
- More flexible, industry standard
- Consistency with other software (Nuke, Maya)
- Complex setup
- Slight performance overhead

Recommendation:
- Small projects: Use RCM
- Large/VFX-heavy: Use OCIO

Setup OCIO in Resolve:
1. Project Settings → Color Management → OpenColorIO
2. Select config.ocio file
3. Choose input color space (auto-detect or manual)
4. Select display and view
5. Verify with test chart
```

**Nuke OCIO Setup:**

```
Nuke OCIO Integration:

1. Environment variable:
   export OCIO=/path/to/config.ocio

2. OCIOColorSpace node:
   - Choose input color space
   - Choose output color space
   - Apply transform

3. OCIOViewer:
   - Set viewer transform
   - Select display and view
   - Check color accuracy

4. OCIOFileTransform:
   - Apply custom LUTs
   - Integrate into OCIO pipeline

Best Practice:
- Use OCIOColorSpace for IDT/ODT
- Use OCIOFileTransform for creative LUTs
- Keep transform chain organized
- Document in node comments
```

## Failure Modes: Transform Chain Errors

### Double Transform Application

**Problem:** Same transform applied twice in pipeline

**Symptoms:**
- Incorrect color reproduction
- Wrong middle gray placement
- Over/under saturation

**Example ACES Pipeline:**

```
Correct:
Camera → IDT → ACES2065-1 → RRT+ODT → Display

Wrong (Double RRT):
Camera → IDT → ACES2065-1 → RRT+ODT → RRT+ODT → Display

Result:
- RRT tone mapping applied twice
- Severe gamma error (extremely dark)
- No shadow detail

Detection:
- Check middle gray placement
- Should be ~40-45% in Rec.709
- If <20%, likely double RRT

Prevention:
- Only apply RRT once, at end of pipeline
- Check OCIO config for transform chains
- Verify with test patterns
```

### Wrong OCIO Config

**Problem:** Software uses wrong or default OCIO configuration

**Symptoms:**
- Colors don't match between software
- Inconsistent transforms
- Missing color spaces

**Detection:**

```
1. Check environment variable:
   echo $OCIO
   Should point to project config.ocio

2. Verify active config in software:
   - Nuke: Node graph → OCIO → Config path
   - Resolve: Project Settings → Color Management → Config
   - Python:ocio.GetCurrentConfig()

3. Test with known input:
   - Create simple gradient
   - Apply transform
   - Compare to reference

Common Mistakes:
- Using "default" OCIO config instead of project config
- Multiple OCIO configs on system, wrong one active
- Config file path error or permission issues
```

### Incompatible Transform Versions

**Problem:** Mixing ACES 1.0 and ACES 1.1+ transforms

**Symptoms:**
- Color mismatch between shots
- Different middle gray placement
- Inconsistent appearance

**ACES Version Differences:**

```
ACES 1.0 (Original):
- Different RRT curve
- Different ODT characteristics
- Specific white point (D60)

ACES 1.1+ (Current):
- Improved RRT (better highlight rolloff)
- Updated ODTs
- D65 white point (matches Rec.709)

Incompatibility:
- ACES 1.0 IDT + ACES 1.1 ODT = Wrong colors
- Middle gray shifts from 10% to 8% highlight
- Skin tones appear different

Solution:
- Use consistent ACES version throughout pipeline
- Upgrade all components to ACES 1.1+
- Regenerate all LUTs with same ACES version
```

### LUT Bake-In During Production

**Problem:** Applying LUTs destructively, losing flexibility

**Example Scenarios:**

```
Scenario 1: Dailies Bake-In
- Production applies Rec.709 LUT to dailies
- Grades baked into editorial
- Final grade limited by early decisions
- Cannot change looks for final

Scenario 2: VFX Bake-In
- VFX vendor applies show LUT to plates
- Composites in display space instead of scene-linear
- Color matching difficult
- Limited flexibility for revisions

Scenario 3: Archive Bake-In
- Archive includes baked creative look
- Cannot re-grade for future formats (HDR)
- Loss of camera-original quality
- Not suitable for archival

Best Practice:
- Archive camera originals (RAW/Log)
- Keep transforms separate (metadata, LUT files)
- Apply LUTs non-destructively in color grading
- Document transform chain for future reference
```

## Mini Glossary: Color Management Pipeline Terms

**OCIO (OpenColorIO):** Open-source color management configuration system developed by Sony Imageworks, now managed by Academy Software Foundation, standard in VFX industry.

**CMS (Color Management System):** Systematic approach to maintaining color accuracy across devices, software, and workflows through standardized transforms and profiles.

**Color Space:** 3D volume of reproducible colors defined by primary chromaticities, white point, and transfer function (Rec.709, P3, ACES, etc.).

**Working Color Space:** Intermediate color space for grading and compositing, chosen for quality and workflow suitability (ACEScg, Rec.709 linear).

**Display Color Space:** Color space optimized for specific display device (Rec.709, P3, HDR), includes display-referred transfer function.

**Scene-Referred:** Image data representing actual scene luminance and color, independent of any display, essential for VFX and flexible grading.

**Display-Referred:** Image data optimized for specific display characteristics (gamma, gamut, brightness), not suitable for further processing.

**Transform Chain:** Sequence of color space conversions (input → working → creative → output), critical for correct color reproduction.

**IDT (Input Device Transform):** Color management transform converting camera-specific imagery (Log/RAW) to standardized working space (ACES, Rec.709 linear).

**ODT (Output Device Transform):** Color management transform converting working color space to display-specific output (Rec.709 gamma 2.4, P3, HDR).

**RRT (Reference Rendering Transform):** ACES transform standardizing scene-referred to output-referred conversion, applied before ODT in ACES pipeline.

**LMT (Look Modification Transform):** Optional ACES transform applied between IDT and RRT+ODT for creative look creation while maintaining ACES pipeline.

**ACES (Academy Color Encoding System):** Color management architecture developed by AMPAS for device-independent color interchange throughout production pipeline.

**ACES2065-1:** ACES scene-linear working space (ACES 2065-1), reference space for all ACES transforms, 16+ stops dynamic range.

**ACEScg:** Working color space derived from ACES2065-1 with AP1 primaries, optimized for color grading and VFX work.

**AP0:** ACES Primaries set 0, using ACES2065-1 XYZ-derived primaries, largest practical gamut.

**AP1:** ACES Primaries set 1, slightly smaller than AP0, used for ACEScg working space.

**Rec.709:** ITU-R BT.709 standard HDTV color space with Rec.709 primaries and BT.1886 gamma 2.4, most common delivery format.

**Rec.2020:** ITU-R BT.2020 Ultra-HD color space with very wide gamut, used for HDR and UHDTV delivery.

**DCI-P3:** Digital Cinema Initiatives P3 color space with wider gamut than Rec.709, used for theatrical projection.

**Display P3:** Apple variant of P3 with D65 white point, used for Apple devices (iPhones, iPads, Macs).

**Gamma:** Power-law transfer function (Y = X^γ) encoding luminance relationship, typically gamma 2.2-2.6 for display-referred.

**BT.1886:** ITU-R recommendation for reference gamma curve in HDTV production, essentially gamma 2.4 with small black level offset.

**OETF (Opto-Electronic Transfer Function):** Camera-side transfer function encoding scene luminance to electrical signal or digital code values.

**EOTF (Electro-Optical Transfer Function):** Display-side transfer function decoding electrical signal to display luminance.

**OOTF (Opto-Optical Transfer Function):** Overall system transfer from scene luminance to display luminance, combination of OETF and EOTF.

**PQ (Perceptual Quantizer):** SMPTE ST 2084 HDR transfer function for absolute luminance encoding up to 10,000 nits, used for Dolby Vision, HDR10.

**HLG (Hybrid Log-Gamma):** ARIB STD-B67 HDR transfer function using relative luminance scaling, backward compatible with SDR.

**HDR (High Dynamic Range):** Imagery with higher dynamic range and/or color gamut than traditional SDR (Standard Dynamic Range).

**SDR (Standard Dynamic Range):** Traditional imagery with ~6 stops DR, Rec.709 gamut, 100 nits peak brightness.

**Nit (cd/m²):** Candela per square meter, unit of luminance used for display brightness specifications.

**Luminance:** Photometric measure of luminous intensity per unit area, perceived as brightness by human eye.

**Chromaticity:** Color quality independent of luminance, defined by hue and saturation (CIE x,y coordinates).

**White Point:** Chromaticity coordinates of reference white (D65 for Rec.709, DCI for P3), defines color balance.

**D65:** Standard illuminant representing average daylight (6504K color temperature), white point for Rec.709 and sRGB.

**DCI White:** Digital Cinema Initiatives white point (x=0.314, y=0.351), slightly greener than D65.

**Primary Chromaticities:** CIE 1931 x,y coordinates defining red, green, and blue primary locations in 2D chromaticity diagram.

**Gamut:** 3D volume or 2D area of reproducible colors within specific color space or display device.

**Gamut Mapping:** Converting colors from source to destination gamut when destination is smaller, using clipping or soft-clipping.

**Tone Mapping:** Dynamic range compression mapping scene-referred HDR to display-referred SDR or HDR output.

**Color Volume:** Maximum range of colors and brightness display can produce (gamut + luminance range).

**ICtCp:** Color representation format used in HDR, separates luminance (I) from chrominance (Ct, Cp), used for HDR signal processing.

**LMS Color Space:** Color space based on human cone responses (Long, Medium, Short wavelengths), used in chromatic adaptation transforms.

**CAT (Chromatic Adaptation Transform):** Mathematical model predicting appearance of colors under different illuminants (Bradford, CAT02).

**Bradford Transform:** Chromatic adaptation transform used in early color management systems, relatively simple but less accurate.

**CAT02:** Chromatic adaptation transform used in CIECAM02 and ACES, more accurate than Bradford.

**Von Kries Adaptation:** Model of chromatic adaptation based on gain control in LMS cone responses, basis for CAT transforms.

**CIECAM02:** Color appearance model predicting perceived color attributes (lightness, chroma, hue) under different viewing conditions.

**IPT Color Space:** Color space designed for perceptual uniformity, better correlates with human perception than CIELAB.

**Jzazbz:** Perceptually uniform color space optimized for HDR and WCG (Wide Color Gamut) applications.

**ICtCp:** Constant luminance color representation used in HDR, more efficient for signal processing than RGB.

**YCbCr:** Color space separating luminance (Y) from chrominance (Cb, Cr color difference signals), used in video compression.

**YUV:** Analog version of YCbCr, used in analog video (PAL, NTSC), term often misused for digital YCbCr.

**YCoCg:** Alternative color space with Co (orange) and Cg (green) chrominance, used in image compression and video coding.

**Subsampling:** Reducing chrominance resolution relative to luminance (4:2:0, 4:2:2, 4:4:4), exploits human eye's lower sensitivity to color detail.

**4:2:0:** Chroma subsampling with full luma resolution, half horizontal and vertical chroma resolution (used in Blu-ray, streaming).

**4:2:2:** Chroma subsampling with full luma resolution, half horizontal chroma resolution only (used in professional production).

**4:4:4:** No chroma subsampling, full resolution for luma and chroma (required for VFX, color grading).

**RGB:** Red, Green, Blue color components, additive color model for displays and digital imaging.

**CMYK:** Cyan, Magenta, Yellow, Black (Key) color components, subtractive color model for print.

**Color Depth:** Number of bits per color channel (8-bit, 10-bit, 12-bit, 16-bit float), determines number of possible colors.

**Bit Depth:** Total bits per pixel (24-bit for 8-bit RGB, 30-bit for 10-bit RGB), sum of all channel bit depths.

**Codec:** COder/DECoder compressing and decompressing video data (ProRes, DNxHD, H.264, HEVC).

**Container:** File format holding encoded video, audio, and metadata (MOV, MXF, MP4).

**Metadata:** Sidecar information describing clip properties (resolution, frame rate, color space, exposure).

**EXIF:** Exchangeable Image File format metadata from digital cameras (ISO, shutter, aperture, white balance).

**XMP:** Extensible Metadata Platform, XML-based metadata standard for embedded metadata in files.

**IPTC:** International Press Telecommunications Council metadata standard for news/photos (caption, keywords, copyright).

**ANCILLARY Data:** Metadata embedded in video signal (VANC, HANC) including timecode, closed captions, SCTE triggers.

**VITC (Vertical Interval Timecode):** Timecode embedded in vertical blanking interval of analog video signal.

**LTC (Linear Timecode):** Timecode recorded on linear audio track of tape, readable during high-speed shuttling.

**Burn-In:** Permanently applying text, timecode, or graphics to video, destructive (cannot be removed).

**Soft Subtitles:** Subtitles delivered as separate text/data track, renderable by player, can be turned on/off.

**Hard Subtitles:** Subtitles burned into video image, cannot be turned off or translated.

**Delivery Format:** Final encoded program meeting broadcaster or platform specifications (codec, color space, loudness, etc.).

**Master:** Highest quality version of program, typically camera originals or uncompressed mezzanine, used for creating deliveries.

**Mezzanine:** Intermediate codec near-original quality but more manageable than uncompressed (ProRes 4444, DNxHR 444).

**Transcode:** Convert from one codec/format to another, typically introducing quality loss.

**Generation Loss:** Quality degradation from multiple encode/decode cycles or transcodes.

**Visually Lossless:** Compression introducing artifacts below threshold of human perception under normal viewing conditions.

**Quality Control (QC):** Systematic review of program for technical compliance and creative standards.

**Technical QC:** Review focusing on technical specifications (color space, levels, audio specs, errors).

**Compliance:** Meeting broadcaster or platform technical requirements (color space, closed captions, loudness).

**Loudness:** Perceived volume of audio, measured in LUFS (Loudness Units Full Scale), specifications vary by platform.

**LKFS:** Loudness K-weighted Full Scale, synonym for LUFS, unit of loudness normalized to full scale digital.

**True Peak:** Maximum absolute level of audio signal after reconstruction, important for preventing clipping.

**Integrated Loudness:** Average loudness over entire program, target -23 to -16 LUFS depending on platform.

**Short-term Loudness:** Average loudness over 3-second window, used for dynamic range measurement.

**Momentary Loudness:** Average loudness over 400ms window, used for monitoring peak loudness.

**LRA (Loudness Range):** Difference between loud and quiet portions, typical values 4-18 LU for broadcast.

**Dolby Atmos:** Object-based audio format with 3D positional audio, up to 128 audio objects.

**5.1 Surround:** Audio format with 5 full-range channels (L, R, C, Ls, Rs) + LFE (subwoofer).

**7.1 Surround:** Audio format with 7 full-range channels (L, R, C, Ls, Rs, Lrs, Rrs) + LFE.

**Stereo:** 2-channel audio (Left, Right), most common delivery format for web and some broadcast.

**Mono:** Single-channel audio, uncommon for modern delivery but used in some archival content.

**Audio Sample Rate:** Samples per second (kHz), common rates 48kHz (video) or 44.1kHz (music).

**Audio Bit Depth:** Bits per audio sample, common depths 16-bit (CD quality) or 24-bit (professional).
