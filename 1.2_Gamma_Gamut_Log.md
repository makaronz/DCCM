# 1.2 Gamma, Gamut, and Logarithmic Encoding

## Theory: OETF, EOTF, OOTF, Transfer Functions

### Transfer Function Definitions

**Transfer function [mathematical relationship mapping signal amplitudes between different stages of the imaging pipeline]** forms the backbone of modern color management. Three critical transfer functions defined by SMPTE ST 2084:2014 and ITU-R BT.2100-2 (2018):

**OETF [Opto-Electronic Transfer Function: camera encoding curve mapping scene linear light to non-linear code values]**:
$$
V = \text{OETF}(L_{scene})
$$

Defined by camera manufacturers (ARRI, Sony, RED). Scene-linear input ($L_{scene}$ in cd/m²) maps to encoded signal ($V$ in code values 0-1023 for 10-bit).

**EOTF [Electro-Optical Transfer Function: display decoding curve mapping code values to emitted light]**:
$$
L_{display} = \text{EOTF}(V)
$$

Defined by display standards (Rec.1886, ST 2084). Encoded signal ($V$) maps to display luminance ($L_{display}$ in cd/m²).

**OOTF [Opto-Optical Transfer Function: combined system response from scene to display]**:
$$
L_{display} = \text{OOTF}(L_{scene}) = \text{EOTF}(\text{OETF}(L_{scene}))
$$

**Creative intent**: OOTF determines appearance. Same scene data appears different on different displays if OOTF varies. HDR mastering requires explicit OOTF control.

### Signal Coding Architectures

**Scene-referred encoding** [image data proportional to scene linear light, preserving dynamic range for color grading]:
- Camera OETF applies
- Wide dynamic range (10-17 stops)
- Logarithmic or perceptual encoding
- Preserves highlight and shadow detail
- Examples: LogC4, S-Log3, REDLog3G10

**Display-referred encoding** [image data optimized for specific display characteristics with clipped highlights]**:
- Display EOTF applied
- Limited dynamic range (6-8 stops for SDR)
- Gamma or PQ/HLG encoding
- Appearance optimized for target display
- Examples: Rec.709, HDR10 (PQ), HLG

**Critical distinction**: Scene-referred = RAW/log before grade. Display-referred = final deliverable. Color grading = scene-referred to display-referred transformation.

### Code Values

**Code value [digital number representing pixel intensity, typically 0-1023 for 10-bit, 0-4095 for 12-bit, normalized 0.0-1.0]**:

**Full range** (data full range): 0-1023 (10-bit), 0-4095 (12-bit), 0.0-1.0 (normalized)
- Used for: Log encoding, RAW, HDR
- Preserves entire signal range
- No headroom/footroom

**Legal range** (video legal range): 64-940 (10-bit), 64-1019 (10-bit Rec.2020)
- Used for: Rec.709/Rec.2020 broadcast
- Headroom/footroom for overshoot/undershoot
- Black = 64, White = 940

**Mapping confusion** causes crushed blacks or clipped highlights. Always verify level mapping in pipeline.

## Gamma Curves: Power Law Functions

### Pure Power Law

$$
V = L^{\gamma}
$$

Where $\gamma$ (gamma) [exponent in power function relationship defining non-linearity] determines curve shape:
- $\gamma = 1.0$: Linear (no encoding)
- $\gamma = 2.2$: CRT natural response
- $\gamma = 1/2.2 \approx 0.45$: sRGB encoding (compensates CRT)
- $\gamma = 2.4$: Rec.1886 display gamma

**Historical context**: CRT displays had inherent $\gamma \approx 2.2$ due to electron gun physics. sRGB/Rec.709 encoding gamma ($\approx 0.45$) pre-distorted signal to compensate for CRT, producing linear end-to-end OOTF.

### Rec.709 OETF (SDR Standard)

**ITU-R BT.709-6 (2015)** defines camera OETF for HD production:

$$
V = \begin{cases}
4.5 \cdot L & \text{for } 0 \leq L < 0.018 \\
1.099 \cdot L^{0.45} - 0.099 & \text{for } 0.018 \leq L \leq 1.0
\end{cases}
$$

**Key characteristics**:
- Linear segment near black (0-0.018) reduces quantization error
- Power law segment (0.45 exponent) for mid-highlights
- Encodes 6-7 stops dynamic range
- 18% gray maps to CV 445/1023 (10-bit)
- 90% reflectance maps to CV 821/1023

**CRITICAL**: Rec.709 OETF applies to CAMERA encoding. Rec.1886 EOTF applies to DISPLAY decoding. Confusing these causes incorrect monitoring (flat or washed-out images).

### Rec.1886 EOTF (Display Gamma)

**ITU-R BT.1886 (2011)** defines reference display EOTF:

$$
L_{display} = (V + b)^{\gamma}
$$

Where:
- $\gamma = 2.4$
- $b = \frac{-1.099}{2.4 \times 4.5} + \sqrt{\left(\frac{1.099}{2.4 \times 4.5}\right)^2 + \frac{0.099}{2.4}}$

The black offset $b$ matches display black level to Rec.709 OETF black output.

**Practical implementation**: Most professional monitors target pure 2.4 gamma (near-zero $b$). Consumer displays vary significantly (2.0-2.4 gamma). Color grading monitors must be calibrated to Rec.1886 2.4.

### sRGB Transfer Function

**IEC 61966-2-1:1999 (sRGB)** differs from Rec.709:

$$
V = \begin{cases}
12.92 \cdot L & \text{for } 0 \leq L < 0.0031308 \\
1.055 \cdot L^{1/2.4} - 0.055 & \text{for } 0.0031308 \leq L \leq 1.0
\end{cases}
$$

**Difference from Rec.709**: Linear segment threshold (0.0031308 vs 0.018) and exponent (1/2.4 vs 0.45). Results in subtly different shadows.

**Confusion risk**: sRGB and Rec.709 often conflated. For cinema, use Rec.709 for HD deliverables. sRGB for web/mobile (computer graphics).

## Logarithmic Encoding

### Logarithmic Curve Mathematics

General form for cinema log curves:

$$
V = a \cdot \log_{10}(c \cdot L + b) + d
$$

Where $a, b, c, d$ are manufacturer-specific parameters controlling:
- $a$: Overall gain/slope
- $b$: Black offset (prevents log(0))
- $c$: Input scaling
- $d$: Output offset (sets black level)

**Advantages of log encoding**:
- Allocates more code values to shadows (human visual sensitivity)
- Compresses highlights (preserves detail without clipping)
- Uniform perceptual contrast across exposure range
- Efficient use of code values (10-bit log ≈ 12-13-bit linear quality)

### LogC4 (ARRI, 2023)

**ALEXA 35 LogC4** [ARRI's latest logarithmic encoding for 17-stop dynamic range, replacing LogC3]:

$$
V = 717 \cdot \log_{10}(5.555555 \cdot L^{(1/4.4)} + 0.016779) + 709
$$

**Key improvements over LogC3**:
- Single curve covers entire 17-stop range (no EI adjustment needed)
- Better shadow SNR [Signal-to-Noise Ratio] through optimized code value allocation
- Cleaner highlights with reduced color crosstalk
- Simplified metadata (single curve vs EI-specific curves)
- Backward compatible with LogC3 workflow

**Mapping** (normalized scene linear to 10-bit code values):
- 0% (noise floor) → CV 95/1023
- 18% gray → CV 599/1023
- 100% reflectance → CV 805/1023
- +6 stops above 18% → CV 928/1023
- Clip point (+7 stops above 100%) → CV 1023/1023

**CRITICAL**: LogC4 requires REVEAL color science v4+ (2023+). Older software (pre-2023) decodes incorrectly, causing magenta cast and wrong contrast.

### S-Log3 (Sony, 2016)

**Sony S-Log3** [logarithmic encoding optimized for 14+ stop dynamic range with single-curve simplicity]:

$$
V = \begin{cases}
420 + \log_{10}(5 \cdot L) \cdot 261.5 & \text{for } L \geq 0 \\
\text{linear portion} & \text{for } L < 0 \text{ (below black)}
\end{cases}
$$

**Key characteristics**:
- Base 10 logarithm (unlike LogC4 which uses power-law preprocessing)
- Single curve for all exposure scenarios
- Normalized scene linear $L=0.0$ maps to CV 95/1023
- 18% gray maps to CV 388/1023
- 100% reflectance (90% white card) maps to CV 596/1023
- Clip point at 10 stops above 18% gray = CV 939/1023

**CineEI mode** [Cine Exposure Index: ISO-independent exposure workflow where EI adjusts metadata but not gain]:
- Set EI based on desired exposure index
- Camera records at base ISO (800/3200 for VENICE 2)
- EI change affects monitoring LUT, not recorded data
- Preserves highlight headroom regardless of EI setting

**Failure mode**: Incorrect white balance metadata causes S-Log3 to display with magenta or green cast in post. Always verify WB on set.

### RED Log3G10

**RED Log3G10** [logarithmic encoding with gain parameter optimized for IPP2 workflow]:

$$
V = 255 \cdot \log_{10}(10^{(4.086 \cdot L + 1.0)} - 1) + 765
$$

**Key characteristics**:
- Base 10 logarithm
- G10 parameter = gain of 10 in formula
- Normalized linear $L=0.0$ maps to CV 128/1023
- 18% gray maps to CV 486/1023
- 100% reflectance maps to CV 681/1023
- Clip point depends on dynamic range setting

**IPP2 workflow** [Image Processing Pipeline 2: RED's color science architecture standardized in 2017]:
- REDWideGamutRGB + Log3G10 as input
- Color space transform to working space (Rec.709, P3, Rec.2020)
- Tone mapping applied after color transform
- Consistent behavior across all RED cameras

### Comparison: LogC4 vs S-Log3 vs RED Log3G10

| Characteristic | LogC4 | S-Log3 | RED Log3G10 |
|---|---|---|---|
| Dynamic range | 17 stops | 14+ stops | 16+ stops (configurable) |
| Base function | Log of power-law | Pure log | Log of exponential |
| 18% gray CV | 599/1023 | 388/1023 | 486/1023 |
| Shadow SNR | Best | Good | Good |
| Highlight roll-off | Smooth | Smooth | Smooth |
| Metadata complexity | Low | Low | Medium |

**Practical implication**: LogC4 appears "brighter" at same exposure because 18% gray maps to higher code value. Grade accordingly.

## HDR Transfer Functions

### PQ (Perceptual Quantizer)

**SMPTE ST 2084:2014 (PQ)** [absolute scale encoding for HDR with 10,000 nit maximum]:

$$
V = \begin{cases}
\frac{c_1 + c_2 \cdot Y^{n_1}}{1 + c_3 \cdot Y^{n_1}} & \text{for } Y > 0 \\
0 & \text{for } Y = 0
\end{cases}
$$

Where $Y$ is normalized luminance ($L/10000$) and constants:
- $c_1 = c_3 - 1 = 3424/4096$
- $c_2 = 2413/4096 \cdot 32/2523$
- $c_3 = 2392/4096 \cdot 32/2523$
- $n_1 = 2610/16384 \cdot 2523/32$

**Key characteristics**:
- Absolute luminance encoding (scene-referred or display-referred)
- 10,000 nit maximum
- Near-perceptual uniformity
- Used for: HDR10, Dolby Vision, Netflix HDR deliverables

**Mastering considerations**:
- Target peak luminance: 1000-4000 nits (typical)
- Content Light Level (CLL): Maximum nit value in frame
- Frame Average Light Level (FALL): Average nits per frame
- Tone mapping required for lower peak displays

### HLG (Hybrid Log-Gamma)

**ARIB STD-B67 (HLG)** [scene-referred HDR encoding designed for broadcast compatibility]:

$$
V = \begin{cases}
\sqrt{3 \cdot L} & \text{for } 0 \leq L \leq 1/12 \\
a \cdot \ln(12 \cdot L - b) + c & \text{for } 1/12 < L \leq 1
\end{cases}
$$

Where constants:
- $a = 0.17883277$
- $b = 0.28466892$
- $c = 0.55991073$

**Key characteristics**:
- Scene-referred (camera OETF)
- Hybrid curve: square root at bottom, log at top
- Automatic backward compatibility with SDR displays
- 1000 nit maximum typical
- Used for: BBC/NHK broadcasts, live events

**System gamma**: HLG relies on display applying appropriate OOTF (different for 100 nit vs 1000 nit displays). No single mastering point.

## Color Gamuts

### Gamut Definitions

**Color gamut [volume of colors reproducible by device within XYZ color space]** defined by:

1. **Primary chromaticities**: (R, G, B) coordinates in xy or u'v'
2. **White point**: Reference white chromaticity (D65, DCI)
3. **Transfer function**: Encoding curve (gamma, log, PQ)

**Gamut boundary**: 2D horseshoe shape in chromaticity diagram, 3D volume in XYZ space including luminance dimension.

### Primary Gamuts in Cinema

**Rec.709** (ITU-R BT.709-6, 2015):
```
Primary Chromaticities:
R: (0.64, 0.33)  G: (0.30, 0.60)  B: (0.15, 0.06)
White: D65 (0.3127, 0.3290)
Coverage: ~35.5% of visible colors (Pointer's gamut)
Standard for: HD broadcast, web, monitoring base
```

**DCI-P3** (SMPTE RP 431-2, 2011):
```
Primary Chromaticities:
R: (0.680, 0.320)  G: (0.265, 0.690)  B: (0.150, 0.060)
White: DCI (0.314, 0.351)
Coverage: ~45.5% of visible colors
Standard for: Digital cinema projection
```

**P3-D65** (DCI-P3 primaries with D65 white):
```
Primary Chromaticities:
R: (0.680, 0.320)  G: (0.265, 0.690)  B: (0.150, 0.060)
White: D65 (0.3127, 0.3290)
Coverage: ~45.5% of visible colors
Standard for: SDR mastering, modern displays, web HDR
```

**Rec.2020** (ITU-R BT.2020-2, 2015):
```
Primary Chromaticities:
R: (0.708, 0.292)  G: (0.170, 0.797)  B: (0.131, 0.046)
White: D65 (0.3127, 0.3290)
Coverage: ~75.8% of visible colors
Standard for: UHDTV, HDR master, future-proofing
```

**Practical workflow**:
- **Capture**: Wide camera-native gamut (AWG, S-Gamut3, REDWideGamutRGB)
- **Master**: Rec.2020 container for HDR delivery
- **Display**: P3 or Rec.709 depending on target

**Camera-native gamuts** (2024-2025):
- **ARRI Wide Gamut (AWG)**: Slightly larger than P3, optimized for skin tones
- **S-Gamut3**: Larger than Rec.2020, designed for maximum color capture
- **S-Gamut3.Cine**: Slightly smaller than S-Gamut3, easier grading
- **REDWideGamutRGB**: Larger than Rec.2020, designed for IPP2 workflow

### Gamut Mapping Strategies

**Out-of-gamut colors** [colors in source gamut not reproducible in target gamut] require mapping strategy:

**1. Hard clip**:
$$
C_{out} = \begin{cases}
C_{max} & \text{if } C_{in} > C_{max} \\
C_{in} & \text{otherwise}
\end{cases}
$$
- Simple truncation at gamut boundary
- Causes hue shifts and detail loss
- Rarely used in professional workflows

**2. Soft clip**:
- Roll-off near boundary
- Preserves detail but reduces saturation
- Common in camera OETFs (log highlights)

**3. Gamut mapping** (hue-preserving):
- Preserve hue angle
- Compress saturation proportionally
- Maintain relative color relationships
- Used in ACES RRT+ODT

**4. Perceptual mapping**:
- Minimize $\Delta E$ overall appearance
- May sacrifice hue accuracy for better appearance
- Used in color appearance models (CAM16, iCAM)

**ACES workflow** [Academy Color Encoding System: standardized color management framework for cinema]:
- ACES2065-1: Scene-linear master (unbounded)
- RRT (Reference Rendering Transform): Scene to output-referred
- ODT (Output Device Transform): Output-referred to display
- Provides consistent appearance across devices

## Practice: Monitor Calibration & Measurement

### Display Calibration Workflow

**SDR calibration** (Rec.1886 EOTF, 100 cd/m² white):

1. **Hardware setup**:
   - Warm-up display: 30 minutes minimum
   - Disable auto-brightness, dynamic contrast
   - Set color temperature mode to "native" or "custom"
   - Connect calibration instrument (spectroradiometer preferred)

2. **Primary calibration** (annual):
   - Measure native white point chromaticity
   - Calculate correction matrix to D65
   - Adjust RGB gains to achieve x=0.3127, y=0.3290
   - Verify tolerance: ±0.001 (≈1-2 ΔE)

3. **Gamma calibration** (monthly):
   - Measure luminance at 10 points (0-100% input)
   - Fit gamma curve to target (2.2, 2.4, or BT.1886)
   - Adjust LUT (1D or 3D) for correction
   - Verify tolerance: ±0.02 in gamma (all points)

4. **Luminance calibration** (monthly):
   - Measure white luminance at 100% input
   - Adjust backlight to 100 cd/m² (±5%)
   - For cinema: 48 cd/m² (simulated projection)
   - Verify uniformity: ±10% center-to-corner (9-point grid)

**HDR calibration** (PQ EOTF, 1000 cd/m² white):

1. **HDR-specific setup**:
   - Enable HDR mode in display settings
   - Maximize backlight (typically 100%)
   - Disable local dimming (if possible) for calibration
   - Verify HDR signal chain (HDMI 2.1, DisplayPort 1.4)

2. **PQ curve calibration**:
   - Measure at 20+ points (0-10000 nits)
   - Verify ST 2084 accuracy: ±5% luminance
   - Check roll-off at peak (soft clip not hard clip)
   - Measure actual peak: 1000 nits typical (±10%)

3. **Color gamut calibration**:
   - Measure primary chromaticities (R, G, B)
   - Verify P3 or Rec.2020 coverage
   - Calculate $\Delta u'v'$ from target
   - Tolerance: ±0.002 (≈3 ΔE at primaries)

4. **CLL/FALL metadata**:
   - Measure maximum content light level (CLL)
   - Measure frame average light level (FALL)
   - Embed in HDR metadata for downstream devices

### Calibration Verification

**Daily verification** (colorimeter acceptable):
1. White point: x,y within ±0.002 of D65
2. Gamma: Verify at 5 points within ±0.05
3. Luminance: 100 cd/m² ±5% (SDR), target ±10% (HDR)
4. Uniformity: Visual check of gray ramps

**Weekly verification** (spectroradiometer recommended):
1. Full 21-point gray ramp measurement
2. Primary/secondary color measurements
3. Skin tone patch verification (ColorChecker)
4. Document deviations and schedule recalibration if needed

**Instrument traceability**:
- Annual calibration by manufacturer (NIST-traceable)
- Monthly verification with transfer standard
- Daily validation with known reference
- Maintain calibration certificates

## Failure Modes

### Wrong Gamma Assumption

**Scenario**: Treating log footage as if it were Rec.709 gamma.

**Symptoms**:
- Washed-out, low-contrast image
- Elevated black level (log never reaches true black)
- Incorrect shadow detail (stretched instead of compressed)
- Color grading produces unexpected results (colors shift when adjusting contrast)

**Technical explanation**:
- LogC4/S-Log3 allocate code values differently than Rec.709
- Log: More values in shadows, fewer in highlights
- Rec.709: More uniform distribution
- Applying Rec.1886 2.4 gamma to log = double encoding

**Detection**:
- False color preview shows unusual distribution
- Waveform monitor appears elevated (log floor at CV 95)
- Histogram doesn't reach 0 (black at CV 95, not CV 64)
- Scope shows "compressed" highlights (log roll-off)

**Solution**:
1. Apply proper IDT (Input Device Transform) or LUT
2. Verify transform matches camera and log curve
3. Check for Rec.709 vs Rec.1886 confusion
4. Confirm data vs legal range mapping

**Prevention**:
- Document camera settings in camera report
- Embed metadata in files (camera model, OETF, gamut)
- Use standardized IDTs (ACES, manufacturer LUTs)
- Color grade in scene-referred workflow (IDT first, grade last)

### Illegal Levels

**Level mapping confusion** causes systematic errors:

**Video legal range** (Rec.709/Rec.2020):
- Black: 64/1023 (10-bit), 256/4096 (12-bit)
- White: 940/1023 (10-bit), 3760/4096 (12-bit)
- Total range: 876 code values

**Data full range** (log, HDR, RAW):
- Black: 0/1023 (10-bit), 0/4096 (12-bit)
- White: 1023/1023 (10-bit), 4095/4096 (12-bit)
- Total range: 1024 code values (10-bit)

**Failure modes**:

1. **Encoding legal-range as full-range**:
   - Causes: Crushed blacks (below 64 clipped), elevated black level
   - Detection: Black point at 0 instead of 64 on waveform
   - Solution: Apply legal-to-full LUT before monitoring

2. **Encoding full-range as legal-range**:
   - Causes: Clipped highlights (above 940 clipped), reduced contrast
   - Detection: White point at 940 instead of 1023
   - Solution: Apply full-to-legal LUT after grading for broadcast

3. **Incorrect metadata** (HDR):
   - Causes: Wrong CLL/FALL values, incorrect tone mapping
   - Detection: HDR appears too dark/bright on reference display
   - Solution: Re-measure and update HDR metadata

**Practical workflow**:
- Capture: Full range (log, RAW)
- Grade: Full range (preserve headroom)
- Monitor: Legal range (for Rec.709) or full range (for HDR)
- Deliver: Legal range (broadcast) or full range (web, HDR)

### Clipping vs Compression

**Clipping** [hard limit at maximum code value where all detail above threshold is lost]:
- Mathematical limit: $V_{out} = \min(V_{in}, V_{max})$
- Causes: Abrupt transition, color crosstalk at clip point
- Recovery: Impossible (information destroyed)
- Common in: Rec.709, poorly designed log curves

**Compression** [soft roll-off where highlight detail preserved but with reduced contrast]:
- Smooth transition: $V_{out} = f(V_{in})$ where $f$ has gradual slope
- Preserves detail: No abrupt transitions
- Recovery: Possible through contrast adjustment
- Common in: LogC4, S-Log3, RED Log3G10

**Log encoding behavior**:
- Highlights: Compressed (not clipped) until sensor limit
- Midtones: Near-linear (easy to grade)
- Shadows: Expanded (more code values, better SNR)

**Detection**:
- Waveform monitor: Clipping = flat line at top, compression = gradual roll-off
- Histogram: Clipping = pile-up at right edge, compression = smooth tail
- False color: Clipping = uniform color at highlight, compression = color gradient

**Practical implications**:
- Log footage appears "flat" but contains more highlight detail
- Proper grade reveals compressed highlights
- Overexposed log = clipped (no recovery possible)
- Underexposed log = noisy shadows (log doesn't help)

**Best practices**:
- Expose for highlights (protect from clipping)
- Use false color on set to verify exposure
- Monitor log waveform (not Rec.709)
- Reference skin tones at proper exposure
- ETTR (Expose To The Right) when possible

## Mini Glossary

- **OETF** [Opto-Electronic Transfer Function]: Camera encoding curve mapping scene linear light to code values; defined by camera manufacturers
- **EOTF** [Electro-Optical Transfer Function]: Display decoding curve mapping code values to emitted light; defined by display standards
- **OOTF** [Opto-Optical Transfer Function]: Combined system response from scene to display; determines creative intent
- **Gamma** [Power Law]: Exponent in power function relationship: $Output = Input^{\gamma}$; CRT displays have $\gamma \approx 2.2$
- **Transfer function**: Mathematical relationship mapping signal amplitudes between pipeline stages (camera → display)
- **Code value**: Digital number representing pixel intensity (0-1023 for 10-bit, 0-4095 for 12-bit)
- **Scene-referred**: Image data proportional to scene linear light; wide dynamic range, logarithmic encoding
- **Display-referred**: Image data optimized for specific display characteristics; limited dynamic range, gamma encoding
- **CLL** [Content Light Level]: Maximum content light level in nits for HDR; embedded in HDR metadata
- **FALL** [Frame Average Light Level]: Average brightness per frame for HDR; embedded in HDR metadata
- **SNR** [Signal-to-Noise Ratio]: Ratio of signal power to noise power; higher = cleaner image; measured in dB
- **Log encoding**: Logarithmic transfer function allocating more code values to shadows, compressing highlights
- **Gamut**: Volume of colors reproducible by device within XYZ color space
- **HDR**: High Dynamic Range imaging (typically 1000+ nits peak, 10+ stops)
- **SDR**: Standard Dynamic Range imaging (typically 100 nits peak, 6-7 stops)
- **PQ**: Perceptual Quantizer (ST 2084) - absolute scale HDR encoding for 10,000 nit maximum
- **HLG**: Hybrid Log-Gamma (ARIB STD-B67) - scene-referred HDR encoding for broadcast
- **ACES**: Academy Color Encoding System - standardized color management framework for cinema
- **IDT**: Input Device Transform - converts camera-native data to ACES scene-linear
- **ODT**: Output Device Transform - converts ACES output-referred to display signals
- **LUT**: Look-Up Table - predefined color transformation (1D or 3D)
