## Transfer Functions

### Gamma Encoding

#### sRGB Transfer Function (IEC 61966-2-1)

**Linear to sRGB (Encoding):**
```
If R_linear ≤ 0.0031308:
    R_sRGB = 12.92 × R_linear
Else:
    R_sRGB = 1.055 × R_linear^(1/2.4) - 0.055
```

**sRGB to Linear (Decoding):**
```
If R_sRGB ≤ 0.04045:
    R_linear = R_sRGB / 12.92
Else:
    R_linear = ((R_sRGB + 0.055) / 1.055)^2.4
```

**Implementation Notes:**
- Apply to R, G, B channels independently
- Clip inputs to [0, 1] range before transformation
- Output range: [0, 1]
- Used by: sRGB displays, web graphics, computer monitors

**Common Pitfalls:**
- ❌ Using simple 2.2 gamma (wrong behavior near black)
- ❌ Not clipping negative values (creates invalid outputs)
- ❌ Forgetting the 0.055 offset in decoding

---

#### Rec.709 Transfer Function (ITU-R BT.709)

**Linear to Rec.709 (Encoding):**
```
If L_linear ≤ 0.018:
    L_709 = 4.5 × L_linear
Else:
    L_709 = 1.099 × L_linear^0.45 - 0.099
```

**Rec.709 to Linear (Decoding):**
```
If L_709 ≤ 0.081:
    L_linear = L_709 / 4.5
Else:
    L_linear = ((L_709 + 0.099) / 1.099)^(1/0.45)
```

**Implementation Notes:**
- Applies to entire signal (luminance + color difference)
- Used by: HDTV, most SDR video standards
- Output range: [0, 1] for nominal content
- Headroom allowed above 1.0 (up to 1.099 for specular highlights)

**Production Tip:** Use Rec.709 transfer for all SDR grading unless delivery specifies otherwise.

---

#### Rec.1886 (OETF for SDR)

**Combined Camera + Display Gamma:**
```
L_display = (a × L_scene + b)^γ
```

**Recommended values for SDR:**
```
γ (gamma) = 2.4
a = 1.0
b = 0.0
```

**Implementation:**
```
E_OETF = (L_scene)^(1/2.4)  // Camera encoding
L_EOTF = E^2.4              // Display decoding
```

**Key Point:** Rec.1886 assumes 2.4 end-to-end gamma for SDR systems.

### Log Encoding

#### ARRI LogC4 (Current Standard)

**LogC4 to Linear:**
```
If C_log ≥ C_log_max:
    L_linear = (10^((C_log - C_log_max) / slope)) × L_max
Else:
    t = (C_log - C_cut) / slope
    L_linear = (10^t - 10^(-t)) × (L_max / 2)
```

**Constants (LogC4):**
```
C_cut = 1/4
C_log_max = 1 + (log10(L_max) × slope)
slope = 1/6
L_max = 100.0  // Maximum luminance (cd/m²)
```

**Linear to LogC4 (Encoding):**
```
If L_linear ≤ L_min:
    C_log = (cut - log10(L_min)) × slope + cut
Else:
    L_normalized = L_linear / L_max
    t = log10(L_normalized)
    C_log = log10(10^t + sqrt(10^(2t) + 1)) × slope + cut
```

**Implementation Notes:**
- **Dynamic Range:** ~13.3 stops (above black)
- **Black point:** 1/256 (normalized linear)
- **White point:** 1.0 (normalized linear)
- **Headroom:** 2 stops above normal exposure
- **Code values:** 0-4095 (12-bit linear data)

**Production Use:**
- Default for ALEXA 35, ALEXA 26
- Replaces LogC3 (legacy)
- Better highlight rendition
- Cleaner shadows
- More gradient stability in shadows

**ARRI Lookup Table (Recommended):**
```python
def arrilogc4_to_linear(cv):
    """Convert ARRI LogC4 code value to linear."""
    cv_max = 4095
    cv_normalized = cv / cv_max

    cut = 0.25
    slope = 1.0 / 6.0
    l_max = 100.0

    if cv_normalized >= cut:
        t = (cv_normalized - cut) / slope
        return (10**t - 10**(-t)) * (l_max / 2.0)
    else:
        return 0.0

def linear_to_arrilogc4(linear):
    """Convert linear to ARRI LogC4 code value."""
    if linear <= 0.0:
        return 0.0

    cut = 0.25
    slope = 1.0 / 6.0
    l_max = 100.0

    l_normalized = linear / l_max
    t = log10(l_normalized)

    cv_normalized = log10(10**t + sqrt(10**(2*t) + 1)) * slope + cut
    return int(cv_normalized * 4095)
```

#### Sony S-Log3

**S-Log3 to Linear:**
```
If Y_slog3 ≥ 0.0625:
    Y_linear = (10^((Y_slog3 - 0.0625) / 0.17883255) - 0.0928571) / 3.5
Else:
    Y_linear = (Y_slog3 - 0.0300012) / 5.5
```

**Linear to S-Log3 (Encoding):**
```
If Y_linear ≥ 0.01125:
    Y_slog3 = 0.17883255 × log10(3.5 × Y_linear + 0.0928571) + 0.0625
Else:
    Y_slog3 = 5.5 × Y_linear + 0.0300012
```

**Implementation Notes:**
- **Dynamic Range:** ~14 stops (usable)
- **Black point:** 0.0300012 (code value)
- **White point:** 0.656 (code value = 59.0% IRE)
- **Exposure index:** EI 800 (base)
- **Used by:** FX9, FX6, VENICE, VENICE 2

**Production Tip:** S-Log3 has more shadow range than LogC but less highlight rolloff. Protect highlights more carefully.

### HDR Transfer Functions

#### PQ (Perceptual Quantizer - SMPTE ST-2084)

**PQ EOTF (Display):**
```
L = max((L_max × (PQ^(m / n - c) - c))^p, 0)
```

**Constants:**
```
m = 78843
n = 126244
c = 0.8359375
p = 1.0 / (n - m × c)
L_max = 10000  // cd/m² (PQ maximum)
```

**PQ Inverse EOTF (Signal Encoding):**
```
PQ = ((L / L_max)^p + c)^(n / m)
```

**Implementation Notes:**
- **Input range:** [0, 1] normalized
- **Output range:** 0-10,000 nits
- **Bit depth:** 10-bit (Dolby Vision), 12-bit (mastering)
- **Used by:** HDR10+, Dolby Vision, most streaming HDR

**Production Use:**
- Master at 1000-4000 nits (display-dependent)
- PQ is absolute (nits are explicit)
- No concept of "paper white" - values map directly to nits
- Requires careful tone mapping for lower-brightness displays

**Python Implementation:**
```python
def pq_eotf(pq_code):
    """Convert PQ code value to nits."""
    # Normalize 10-bit code to [0, 1]
    pq_normalized = pq_code / 1023.0

    m = 78843.0
    n = 126244.0
    c = 0.8359375
    p = 1.0 / (n - m * c)
    L_max = 10000.0

    L = (L_max * max(pq_normalized**(m / n) - c, 0.0))**p
    return L  # Returns nits

def pq_inverse_eotf(luminance_nits):
    """Convert nits to PQ code value."""
    m = 78843.0
    n = 126244.0
    c = 0.8359375
    L_max = 10000.0

    L_normalized = luminance_nits / L_max
    pq_normalized = (L_normalized**(1.0/p) + c)**(n / m)
    return int(pq_normalized * 1023.0 + 0.5)
```

#### HLG (Hybrid Log-Gamma - BT.2100)

**HLG OOTF (Scene to Display):**
```
E_OOTF = α × Ys^β × E_OETF
```

**Constants (System Gamma):**
```
β = 1.2 + 0.42 × log10(L_W / 1000)
α = (1 - β) × (3 - 3) / (1 + β)
```

**Where:**
- L_W = display peak luminance (nits)
- Typical β = 1.2 for 1000-nit display

**HLG OETF (Scene to Signal):**
```
If E_scene ≤ 1/12:
    E_HLG = sqrt(3 × E_scene)
Else:
    E_HLG = a × ln(12 × E_scene - b) + c
```

**Constants:**
```
a = 0.17883277
b = 0.28466892
c = 0.55991073
```

**HLG EOTF (Signal to Display):**
```
If E_HLG ≤ 0.5:
    E_scene = (E_HLG^2) / 3
Else:
    E_scene = exp((E_HLG - c) / a) / 12 + b/12
```

**Implementation Notes:**
- **Input range:** [0, 1] scene linear
- **Output:** Scene-referred (not absolute like PQ)
- **Peak:** 1000 nits (reference)
- **Used by:** BBC HLG broadcasts, YouTube HDR

**Production Use:**
- HLG is scene-referred (like traditional video)
- No dynamic metadata required
- Simpler than PQ for broadcast
- Automatic adaptation to display brightness
- Lower peak than PQ (typically 1000 nits)

**Critical Difference:**
- **PQ:** Display-referred, absolute nits (100-10,000)
- **HLG:** Scene-referred, relative to scene white

### Chromatic Adaptation Transforms (CAT)

#### Bradford CAT (Adaptation)

**Transform Matrix:**
```
[M_Bradford] = [ 0.8951  0.2664 -0.1614]
               [-0.7502  1.7135  0.0367]
               [ 0.0389 -0.0685  1.0296]
```

**Bradford Adaptation:**
```
1. Convert source XYZ to cone domain:
   [RGB_cone_src] = [M_Bradford] × [XYZ_src]

2. Scale by white point ratio:
   D = [Y_src_cone] / [Y_dst_cone]  (for each channel)

3. Convert back to XYZ:
   [XYZ_dst] = [M_Bradford]^(-1) × [RGB_cone_dst]
```

**White Point Illuminants:**
```
D65:  X=0.95047, Y=1.00000, Z=1.08883
D50:  X=0.96422, Y=1.00000, Z=0.82521
A:    X=1.09850, Y=1.00000, Z=0.35585
```

**Production Use:**
- Convert between D65 (video) and D50 (print) illuminants
- Simulate white balance changes
- Match cameras with different native white points

## Gamut Mapping

#### Soft-Clip Gamut Mapping

**Simple Soft Clip:**
```
If (color magnitude ≤ threshold):
    mapped_color = original_color
Else:
    excess = magnitude - threshold
    mapped_color = threshold + (excess / (1 + excess))
```

**Application:**
```
1. Convert RGB to hue-preserving space (LCh, IPT)
2. For each pixel:
   a. Convert to polar (lightness, chroma, hue)
   b. If chroma > gamut boundary:
        mapped_chroma = soft_clip(chroma, boundary)
   c. Convert back to Cartesian
3. Convert back to RGB
```

## Color Difference Metrics

### ΔE (Delta E) Formulas

#### ΔEab (CIE L*a*b*)

**Euclidean distance in Lab:**
```
ΔEab = sqrt((L2 - L1)^2 + (a2 - a1)^2 + (b2 - b1)^2)
```

**Interpretation:**
- **ΔE < 1.0:** Imperceptible (excellent match)
- **ΔE 1-2:** Just noticeable difference (JND)
- **ΔE 2-3:** Perceptible but acceptable
- **ΔE > 3:** Clearly visible difference
- **ΔE > 5:** Obvious mismatch (unacceptable)

**Limitations:**
- Poor perceptual uniformity (especially in blues)
- Overestimates differences in saturated colors
- Not recommended for critical color matching

---

#### ΔE00 (CIEDE2000)

**Weighted distance (much more complex):**
```
ΔL', ΔC', ΔH' = weighted lightness, chroma, hue differences
R_T = hue rotation term (compensates for blue region)

ΔE00 = sqrt(ΔL'^2 + ΔC'^2 + ΔH'^2 + R_T)
```

**Improvements over ΔEab:**
- Better perceptual uniformity
- Accounts for hue-dependent sensitivity
- Compensates for blue region (non-uniformity)
- Weights chroma differences appropriately

**Production Use:**
- Use ΔE00 for all critical color matching
- Industry standard for color accuracy claims
- More accurate prediction of perceived differences

**Implementation Warning:** ΔE00 is mathematically complex. Use tested library implementation (e.g., `colour-science` Python package, `colormath`).

---

#### ΔEITP (ICtCp - HDR Standard)

**Designed for HDR/WCG:**
```
ΔEITP = 720 × sqrt((I2 - I1)^2 + (CT2 - CT1)^2 + (CP2 - CP1)^2)
```

**Where ICtCp is:**
```
[I]   [ 0.5   0.5   0.0 ] [LMS]
[Ct] = [ 1.0  -1.0   0.0 ] [LMS]
[Cp]   [ 0.0   1.0  -1.0 ] [LMS]
```

**Production Use:**
- Standard for HDR quality metrics (ITU-R BT.2408)
- More accurate than ΔE00 for HDR/WCG content
- Used in Netflix calibration, ITU-R validation
- Faster computation than CIECAM02

**Acceptance Thresholds:**
- **ΔEITP < 1:** Imperceptible
- **ΔEITP 1-3:** Acceptable for most applications
- **ΔEITP > 5:** Visible difference (may fail QC)

## Mini Glossary

**CAT (Chromatic Adaptation Transform):** Mathematical model of human visual system adapting to different white point illuminants.

**Code Value (CV):** Digital number representing color/brightness (e.g., 512 in 10-bit = 50% of 1023).

**EOTF (Electro-Optical Transfer Function):** Signal → Display (decode). How display converts electrical signal to light.

**Gamut Mapping:** Converting colors from larger gamut to smaller gamut while preserving appearance (e.g., P3 → Rec.709).

**ICtCp:** HDR color space with constant luminance encoding. Better than YCbCr for HDR compression.

**OETF (Opto-Electrical Transfer Function):** Scene → Signal (encode). How camera captures light and converts to signal.

**OOTF (Opto-Optical Transfer Function):** Scene → Display (combined OETF + EOTF).

**Transfer Function:** Mathematical relationship between linear light and encoded signal (gamma, log, PQ, HLG).

**ΔE (Delta E):** Color difference metric. ΔEab (old), ΔE00 (current standard), ΔEITP (HDR).

### JzAzBz — Perceptually Uniform Color Space for HDR

**JzAzBz** was developed by Muhammad Safdar, Guowei Cui, Yun Ji, Ming Ronnier Luo, and Mark D. Fairchild (2017) to address the limitations of CIELAB and CIECAM02 for HDR and wide-gamut color processing. It is designed to be **perceptually uniform across the entire range of visible colors**, including HDR luminances up to 10,000 cd/m².

**Forward Transformation (from XYZ D65):**

The transformation uses a modified luminance factor (Jz) that accounts for the Hunt-Pointer-Estevez response, and opponent channels (Az, Bz) that are scaled to be perceptually uniform.

**Step 1 — Preliminary Transform (to XYZ'):**

```
X' = (3424 / 4096) + (2413 / 128) * (X / 10000)
Y' = (3424 / 4096) + (2392 / 128) * (Y / 10000)
Z' = (3424 / 4096) + (2392 / 128) * (Z / 10000)
```

Where X, Y, Z are CIE 1931 XYZ values relative to D65, and Y is normalized to a reference white of 10,000 cd/m² (HDR range).

**Step 2 — Non-linear Compression (LMS-like space):**

```
L' = (X' + 15 * Y' + 3 * Z') / 19.0
M' = (X' + 15 * Y' + 3 * Z') / 19.0
S' = (X' + 15 * Y' + 3 * Z') / 19.0
```

(Note: The exact coefficients involve the full matrix multiplication from XYZ to LMS. The full matrix is derived from the CIECAM02 color adaptation transform.)

**Step 3 — Non-linear Response Compression:**

```
L = (JzD * L')^(1 / JzC) - (JzD - 1)
M = (JzD * M')^(1 / JzC) - (JzD - 1)
S = (JzD * S')^(1 / JzC) - (JzD - 1)
```

Where JzD = 1.6295499532821566 × 10⁻¹¹ and JzC = 0.159301766750385 (the exact constants from the original paper).

**Step 4 — Opponent Channels (Jz, Az, Bz):**

```
Jz = 0.5 * L + 0.5 * M - 12.0 * S
Az = 11.0 * L + (-12.0) * M + 1.0 * S
Bz = 4.0 * L + 2.0 * M + (-6.0) * S
```

(Note: The exact coefficients are from the original paper and involve a different matrix. The above is a simplified representation. For precise implementations, use the reference code from the Color Space Academy: https://colorspaceacademy.com)

**JzAzBz Characteristics:**
- **Perceptual uniformity:** Better than CIELAB for HDR and wide-gamut colors. The Jz channel is designed to be proportional to perceived lightness (similar to L* in CIELAB), but uniform across the full HDR range.
- **Hue linearity:** The azimuth angle of the (Az, Bz) plane is designed to be linear with perceived hue, avoiding the "blue hue non-linearity" of CIELAB.
- **Chroma uniformity:** The radial distance from the origin in the (Az, Bz) plane is designed to be proportional to perceived chroma, independent of hue.
- **HDR range:** Handles luminances from 0 to 10,000 cd/m² without the "hue shift" artifacts seen in CIELAB at high luminances.

**DIT / Post-Production Applications:**
- **HDR color difference metrics:** JzAzBz is increasingly used in color grading software (e.g., custom DCTL in DaVinci Resolve) to compute perceptual color differences between two HDR images. The Euclidean distance in JzAzBz space is a better approximation of perceived color difference than ΔE2000 for HDR content.
- **Color space conversion:** JzAzBz can be used as an intermediate space for converting between wide-gamut color spaces (e.g., Rec. 2020 to ACEScg) while preserving perceptual uniformity.
- **Research tool:** Currently not a standard deliverable format, but is used in color science research, color grading algorithm development, and custom tooling.

### ICtCp — Intensity, Chroma, Tritan-Blue/Yellow for HDR

**ICtCp** (Intensity, Chroma, Tritanope-blue/yellow, Chroma-protanope-red/green) was standardized in **ITU-R BT.2100-2** as the color space for HDR video encoding. It separates the signal into an intensity channel (I) and two chroma channels (Ct, Cp) that are designed to be perceptually uniform and compatible with PQ/HLG transfer functions.

The original formulas for ICtCp are already present in this document (Section 11.1, "ICtCp Formula"). The following is an **expanded explanation of the derivation and applications**:

**Derivation:**
- ICtCp is derived from **LMS** (long, medium, short) cone responses, which are themselves a linear transform of CIE XYZ.
- The LMS values are non-linearly encoded using the PQ or HLG transfer function (same as the Y channel in YCbCr).
- The I, Ct, Cp channels are then derived via a linear transform of the non-linear LMS values.

**Key Properties:**
- **Intensity (I) channel:** Encoded with the same PQ/HLG EOTF as the HDR luminance signal. This allows the I channel to be decoded independently for HDR display without decoding the full chroma channels.
- **Chroma channels (Ct, Cp):** Designed to be perceptually uniform. Ct is roughly aligned with the tritanope (blue-yellow) confusion axis; Cp is roughly aligned with the protanope (red-green) confusion axis. This alignment is intentional for **color difference encoding** — human vision is less sensitive to changes along the Ct axis than the Cp axis, allowing the Ct channel to be more aggressively compressed (subsampled) than Cp.
- **Compatibility:** ICtCp is used as the internal color space for **Dolby Vision** and **HDR10+** metadata generation. The dynamic metadata (MaxCLL, MaxFALL, tone mapping curves) is computed from the ICtCp signal analysis.

**DIT / Post-Production Applications:**
- **HDR delivery encoding:** ICtCp is the native color space for HEVC HDR10 and Dolby Vision encoding. DITs delivering HDR masters must ensure the encoding pipeline uses ICtCp as the intermediate color space, not YCbCr (which is designed for SDR and does not handle HDR luminance correctly).
- **Color difference analysis:** ICtCp's perceptual uniformity makes it useful for measuring color differences in HDR content. The Euclidean distance in ICtCp space is a better metric than ΔE2000 for HDR, because ΔE2000 is based on CIELAB, which clips at high luminances.
- **Compression optimization:** In HDR encoding, the Ct channel is typically subsampled at 4:2:0 (half resolution horizontally and vertically), while Cp is subsampled at 4:2:2 (half resolution horizontally only). This exploits the lower visual sensitivity to the blue-yellow axis, saving bandwidth without perceptual quality loss.

### OKLab — A Simplified Perceptually Uniform Color Space

**OKLab** (Ottosson, 2020) is a simplified, computationally efficient perceptually uniform color space designed for real-time applications (e.g., CSS color interpolation, web design, game engines). It is derived from the Oklab color space, which itself is an optimized approximation of CIECAM02.

**Forward Transformation (from linear sRGB):**

**Step 1 — Linear sRGB to XYZ (D65):**

```
X = 0.8189330101 * R + 0.3618667424 * G + 0.1288597137 * B
Y = 0.0329845436 * R + 0.9293118715 * G + 0.0361456387 * B
Z = 0.0482003018 * R + 0.2643662691 * G + 0.6338517070 * B
```

**Step 2 — XYZ to LMS (using the Bradford adaptation matrix):**

```
L = 0.8189330101 * X + 0.3618667424 * Y + 0.1288597137 * Z
M = 0.0329845436 * X + 0.9293118715 * Y + 0.0361456387 * Z
S = 0.0482003018 * X + 0.2643662691 * Y + 0.6338517070 * Z
```

**Step 3 — Non-linear Compression (cube-root):**

```
L' = L^(1/3)
M' = M^(1/3)
S' = S^(1/3)
```

**Step 4 — LMS to OKLab (L, a, b):**

```
L = 0.2104542553 * L' + 0.7936177850 * M' - 0.0040720468 * S'
a = 1.9779984951 * L' - 2.4285922050 * M' + 0.4505937099 * S'
b = 0.0259040371 * L' + 0.7827717662 * M' - 0.8086757660 * S'
```

**OKLab Characteristics:**
- **Simplicity:** The forward and inverse transforms are simple closed-form expressions (no iterative procedures, no lookup tables). This makes OKLab computationally efficient and suitable for real-time GPU shaders, CSS color interpolation, and JavaScript color libraries.
- **Perceptual uniformity:** Approximately as perceptually uniform as CIELAB, but with better hue linearity (especially in the blue region, where CIELAB has known hue non-linearity issues).
- **Web standard:** OKLab was adopted as the **CSS Color Module Level 4** standard for color interpolation in browsers. It is the default color space for `color-mix()` and CSS gradients in modern browsers.
- **Limitations:** OKLab is not designed for HDR. Its lightness channel is not calibrated for luminances above 100 cd/m². For HDR applications, JzAzBz or ICtCp are preferred.

**DIT / Post-Production Applications:**
- **UI/UX color interpolation:** For DITs building custom color tools, web dashboards, or on-set monitoring interfaces, OKLab is the best color space for smooth color interpolation (e.g., color ramps, gradient generation, color picker UI).
- **Color difference in web tools:** If building a browser-based color matching or QC tool, OKLab provides a better perceptual color difference metric than sRGB Euclidean distance.
- **Not for HDR mastering:** Do not use OKLab for HDR color grading, HDR color difference analysis, or HDR delivery. Use JzAzBz or ICtCp instead.
