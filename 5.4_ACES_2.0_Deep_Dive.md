# 5.4 ACES 2.0 Deep Dive

## 5.4.1 Theory: ACES 2.0 Architecture and Components

### 5.4.1.1 Overview of ACES 2.0

The Academy Color Encoding System 2.0 represents a fundamental rethinking of color management for digital cinema, building upon the foundation laid by ACES 1.x while addressing its limitations and incorporating advances in color science. As of 2024-2025, ACES 2.0 represents the current evolution of the system, with significant improvements in HDR workflow support, color appearance modeling, and transform architecture.

**ACES 2.0 Development Status (2024-2025):**
- ACES 2.0 is under active development by the Academy of Motion Picture Arts and Sciences
- Early adopter implementations began in 2023
- Production testing is ongoing as of 2025
- Official release expected following final validation phases (verify current status)

The transition from ACES 1.x to 2.0 is not merely incremental—it reflects a paradigm shift in how color transforms are structured and applied, particularly for HDR content and modern display technologies.

### 5.4.1.2 Architectural Changes from ACES 1.x

**ACES 1.x Architecture:**

ACES 1.x established a clear but rigid pipeline:
```
Input → IDT → ACES 2065-1 → RRT+ODT → Output
```

The Reference Rendering Transform (RRT) and Output Device Transform (ODT) were coupled as "RRT+ODT" transforms, applying both a creative rendering and device-specific output in a single step.

**ACES 2.0 Architecture:**

ACES 2.0 introduces a more flexible approach:
```
Input → IDT → ACES 2065-1 → RRT (standalone) → ODT (device-specific) → Output
```

This decoupling offers several advantages:

1. **Separate RRT and ODT**: The creative rendering (RRT) is now independent from device mapping (ODT), allowing for more flexible grading and display targeting.
2. **Improved HDR support**: The new architecture better accommodates high dynamic range workflows.
3. **Enhanced color appearance**: Integration of Color Appearance Modeling (CAM) improves perceptual uniformity.
4. **Transform chain flexibility**: Artists can apply creative grading after the RRT but before the ODT.

**Key Architectural Differences:**

| Aspect | ACES 1.x | ACES 2.0 |
|--------|---------|----------|
| RRT/ODT coupling | Combined as RRT+ODT | Separate transforms |
| HDR support | Limited (ACES 1.3 extensions) | Native support |
| Color appearance | Limited CAM integration | Full CAM integration |
| Transform naming | RRT+ODT naming scheme | Individual RRT and ODT names |
| OCIO version | OCIO 1.x compatible | Requires OCIO 2.0+ |

### 5.4.1.3 Color Appearance Modeling (CAM) in ACES 2.0

**What is CAM?**

Color Appearance Modeling [a mathematical model that predicts how colors appear to human observers under varying viewing conditions] plays a central role in ACES 2.0. The integration of CAM addresses perceptual non-uniformities that were present in ACES 1.x transforms.

**Why CAM Matters:**

In ACES 1.x, certain color relationships and brightness transitions did not appear perfectly natural to human vision, particularly in highlight rolloff, shadow detail, and saturated colors. CAM provides a framework to ensure that color relationships are preserved according to human perception rather than just mathematical linearity.

**CAM in ACES 2.0:**

The ACES 2.0 RRT incorporates Color Appearance Modeling to:

1. **Improve perceptual uniformity**: Colors and tones appear more natural to human vision
2. **Enhance highlight rolloff**: Smoother, more natural highlight transitions
3. **Better shadow separation**: Improved detail visibility in dark regions
4. **Accurate saturation**: Colors maintain saturation relationships more consistently across luminance levels

**Technical Details:**

- The ACES 2.0 CAM implementation is based on contemporary color appearance research (verify specific CAM model—likely based on ZCAM or similar modern appearance models)
- CAM parameters are tuned for typical cinema viewing environments
- The modeling accounts for viewing environment luminance, surround, and adaptation

### 5.4.1.4 The New Reference Rendering Transform (RRT)

**Purpose of the RRT:**

The Reference Rendering Transform [a standardized creative rendering that converts scene-referred ACES data to output-referred display-ready values] in ACES 2.0 serves as a creative starting point, similar in spirit to film print emulation.

**Changes in ACES 2.0 RRT:**

Compared to ACES 1.x, the ACES 2.0 RRT features:

1. **CAM-based rendering**: Incorporates color appearance modeling for more natural appearance
2. **Improved tonal mapping**: Better handling of extreme dynamic range
3. **Refined color rendition**: More accurate color relationships, particularly for highly saturated colors
4. **Enhanced highlight handling**: More film-like highlight rolloff
5. **Optimized shadow detail**: Better separation in dark tones without crushing

**RRT Application:**

In ACES 2.0 workflows, the RRT is applied as a standalone transform after the ACES 2065-1 scene-referred data and before the ODT:

```
ACES 2065-1 (scene-referred) → RRT (output-referred) → ODT (display-ready)
```

This allows for creative grading in the output-referred space after the RRT but before display-specific mapping.

### 5.4.1.5 Updated Output Device Transforms (ODTs)

**ODT Evolution:**

ACES 2.0 introduces updated ODTs for both HDR and SDR displays:

**HDR ODTs:**

1. **PQ ODTs**: For Dolby Vision PQ mastering (1000, 2000, 4000 nits)
2. **HLG ODTs**: For Hybrid Log-Gamma broadcasts (BBC/NHK standard)
3. **Legacy HDR ODTs**: Updated versions for compatibility with existing HDR workflows

**SDR ODTs:**

1. **Rec.709 ODT**: Updated for improved SDR grading
2. **P3 ODT**: For DCI-P3 theatrical projection (verify if updated)
3. **sRGB ODT**: For monitoring on sRGB displays

**Key ODT Changes:**

1. **Decoupled from RRT**: ODTs now only handle display-specific mapping
2. **Improved HDR accuracy**: Better tone mapping for HDR displays
3. **Refined SDR rendering**: More perceptually uniform SDR output
4. **Better gamut mapping**: Improved handling of out-of-gamut colors

**ODT Naming Convention:**

ACES 2.0 uses a new naming convention that reflects the decoupled architecture:
- ACES 1.x: `ACES - RRT+ODT - [Display] - [Transfer]`
- ACES 2.0: `ACES - RRT` (standalone) and `ACES - ODT - [Display] - [Transfer]`

### 5.4.1.6 Input Device Transforms (IDTs) in ACES 2.0

**IDT Purpose:**

Input Device Transforms [convert camera-specific RGB values to the ACES 2065-1 scene-referred color space] remain the first step in the ACES pipeline, but ACES 2.0 introduces updates and additions.

**New IDT Developments:**

1. **Modern camera support**: IDTs for current cinema cameras (Arri Alexa 35, RED V-Raptor, Sony Venice 2, etc.)
2. **Improved metadata handling**: Better use of camera metadata for accurate transforms
3. **RAW processing integration**: Enhanced integration with RAW processing workflows
4. **Legacy camera support**: Continued support for older cameras with updated transforms

**IDT Categories:**

- **Manufacturer-specific IDTs**: Custom transforms from camera manufacturers (Arri, RED, Sony, etc.)
- **Generic IDTs**: ACES-constructed IDTs for cameras without manufacturer transforms
- **Experimental IDTs**: Community-developed transforms for newer cameras

**IDT Updates:**

ACES 2.0 IDTs benefit from:
- Improved color science research
- Better characterization of camera spectral sensitivities
- Enhanced handling of camera-specific noise and artifacts
- Integration with modern RAW processing pipelines

## 5.4.2 Practice: Implementing ACES 2.0

### 5.4.2.1 Migration from ACES 1.x to ACES 2.0

**Migration Strategy:**

Transitioning from ACES 1.x to ACES 2.0 requires careful planning due to the significant architectural changes. The migration path depends on project phase and existing deliverables.

**For New Projects:**

Starting fresh with ACES 2.0 is straightforward:
1. Use ACES 2.0 OCIO configuration
2. Select ACES 2.0 transforms (RRT, ODT, IDT)
3. Follow updated naming conventions
4. Leverage new HDR capabilities

**For Ongoing Projects:**

Migrating an active ACES 1.x project to ACES 2.0 requires consideration:
- **Grade compatibility**: Existing grades may need adjustment due to RRT changes
- **Deliverables**: Confirm whether ACES 1.x or 2.0 is required for deliverables
- **Shot consistency**: Ensure all shots use the same ACES version
- **Client requirements**: Verify client specifications for ACES version

**Regrading Considerations:**

When migrating graded shots from ACES 1.x to ACES 2.0:

1. **Creative intent may shift**: The new RRT applies different rendering, so grades will not match exactly
2. **Start fresh if possible**: For creative control, regrade from ACES 2065-1 using ACES 2.0 RRT
3. **Grade matching**: If matching is required, use ACES 1.x RRT+ODT for reference and adjust ACES 2.0 grade accordingly
4. **Document changes**: Keep records of grade adjustments for future reference

**Project Stages and Migration:**

| Project Stage | ACES 2.0 Migration Approach |
|---------------|-----------------------------|
| Pre-production | Plan for ACES 2.0 from the start |
| Production | Capture ACES 2065-1 data (version-agnostic) |
| Early post | Good time to adopt ACES 2.0 |
| Mid-post (ungraded) | Can migrate with testing |
| Late post (graded) | Careful consideration of regrade effort |
| Deliverables | May be locked to ACES 1.x if already rendered |

### 5.4.2.2 ACES 2.0 OCIO Configuration

**OCIO 2.0 Requirement:**

ACES 2.0 requires OpenColorIO 2.0 or later due to architectural changes in transform handling.

**Configuration File Differences:**

ACES 2.0 OCIO configs differ from ACES 1.x in several ways:

1. **Separate RRT and ODT roles**: The decoupled architecture is reflected in the config structure
2. **Updated color space definitions**: New and updated color spaces for ACES 2.0 transforms
3. **Transform naming**: New naming convention for clarity
4. **Versioning**: ACES version is clearly specified

**Sample ACES 2.0 OCIO Config Structure:**

```yaml
# ACES 2.0 OCIO configuration structure (simplified)
colorspaces:
  - !<ColorSpace>
    name: ACES - ACES2065-1
    family: ACES
    description: ACES 2065-1 (scene-referred)

  - !<ColorSpace>
    name: ACES - RRT
    family: ACES
    description: ACES 2.0 Reference Rendering Transform
    from_reference: !<GroupTransform>
      children:
        - !<FileTransform> {src: rrt.ctl}

  - !<ColorSpace>
    name: ACES - ODT - Rec709 - 100nits
    family: ACES
    description: ACES 2.0 ODT for Rec.709 SDR
    from_reference: !<GroupTransform>
      children:
        - !<FileTransform> {src: odt_rec709_100nits.ctl}

roles:
  aces_interchange: ACES - ACES2065-1
  rendering: ACES - RRT
  output: ACES - ODT - Rec709 - 100nits  # Example default output
```

**Key Roles in ACES 2.0:**

- `aces_interchange`: The ACES 2065-1 color space (unchanged from ACES 1.x)
- `rendering`: The RRT (new role in ACES 2.0)
- `output`: Default ODT (display-specific)

**Display-Referred Working Space:**

ACES 2.0 introduces the concept of a display-referred working space after the RRT:
- Apply RRT to convert from scene-referred (ACES 2065-1) to output-referred
- Perform creative grading in output-referred space
- Apply ODT for final display mapping

**Obtaining ACES 2.0 OCIO Configs:**

- **Official release**: Download from the Academy's ACES website when available (verify availability as of 2025)
- **Development versions**: Available from ACES GitHub repository for testing
- **Vendor configs**: Some software vendors provide ACES 2.0 configs (DaVinci Resolve, Baselight, etc.)

### 5.4.2.3 Workflow Adjustments for ACES 2.0

**Colorist Workflow:**

The decoupled RRT+ODT structure in ACES 2.0 enables a modified colorist workflow:

**Traditional ACES 1.x Workflow:**
```
Camera → IDT → ACES 2065-1 → Grade → RRT+ODT → Display
```

**ACES 2.0 Workflow:**
```
Camera → IDT → ACES 2065-1 → RRT → Grade → ODT → Display
```

**Key Differences:**

1. **Grade position**: Creative grading now occurs after the RRT in output-referred space
2. **Flexible ODT switching**: Can preview different output targets without reapplying the RRT
3. **Improved HDR preview**: Better HDR monitoring during grading
4. **Display-referred grading**: Grading in output-referred space requires adjustment to working methods

**Grading After RRT: Benefits and Considerations:**

**Benefits:**
- More intuitive starting point for colorists (resembles a "look")
- Consistent creative rendering across shots
- Easier matching of shots graded at different times
- Better preview of final appearance

**Considerations:**
- Working in output-referred space (not scene-linear)
- Different behavior for operations like power curves
- Need to understand the impact of the RRT on the image
- May require different grading approaches than scene-linear grading

**VFX Workflow:**

For VFX and CGI work, ACES 2.0 maintains the scene-referred workflow:

```
CG render (scene-linear) → ACES 2065-1 → Compositing → RRT → ODT → Display
```

**Key Points:**
- Keep VFX in scene-linear ACES 2065-1 as long as possible
- Apply RRT only when transitioning to output-referred (typically in final color)
- Use ACES-compliant rendering and compositing tools
- Ensure all elements use consistent ACES version

**HDR Workflow:**

ACES 2.0's improved HDR support enables better HDR finishing:

1. **Grade for HDR first**: Master in HDR (e.g., 1000 nit PQ)
2. **Apply RRT**: Use ACES 2.0 RRT for rendering
3. **HDR ODT**: Apply HDR ODT for target display
4. **SDR downconversion**: For SDR deliverables, use appropriate SDR ODT

**Monitoring and Preview:**

ACES 2.0 monitoring strategies:
- **Reference display**: Use a calibrated display matching the target ODT
- **Simultaneous preview**: Some tools allow multiple ODT previews simultaneously
- **LUT-based monitoring**: Use LUTs derived from ACES 2.0 transforms for monitoring
- **Software emulation**: Use OCIO to emulate different output targets on a single display

### 5.4.2.5 Versioning and Backward Compatibility

**Version Coexistence:**

In transition periods, ACES 1.x and ACES 2.0 may coexist:

**Version-Specific OCIO Configs:**
- Maintain separate OCIO configs for ACES 1.x and ACES 2.0
- Clear naming to avoid confusion
- Document which projects use which version

**Transform Versioning:**
- ACES 2.0 transforms have distinct names from ACES 1.x
- Using the wrong version transforms causes visual differences
- Always confirm transform versions when setting up shots

**Deliverable Specifications:**

When delivering ACES-managed content:
- Specify ACES version in deliverable specs

**Archive Considerations:**

When archiving ACES projects:

- Document the complete transform chain
- Consider archiving graded results for reference

## 5.4.3 Failure Modes: ACES 2.0 Challenges and Solutions

### 5.4.3.1 Version Conflicts and Mismatches

**Symptom: Visual Inconsistency Between Shots**

**Cause:**
- Some shots graded with ACES 1.x RRT+ODT, others with ACES 2.0 RRT+ODT
- Inconsistent transform application across shots
- Mixed IDT versions for same camera

**Diagnosis:**
1. Check OCIO config version for each shot
2. Verify transform names in node graphs or grades
3. Review shot metadata for transform information
4. Use OCIO's color space information to verify active transforms

**Prevention:**
- Establish ACES version at project start
- Use consistent OCIO config across all shots
- Document ACES version in project specifications
- Use automated checks to catch version mismatches

**Resolution:**
1. Identify all shots using incorrect ACES version
2. Re-grade affected shots using correct ACES 2.0 transforms
3. Use shot matching tools to match reference grades
4. Re-render all deliverables from corrected grades

**Symptom: Grade Looks Wrong After Software Update**

**Cause:**
- Software updated defaults to new ACES version
- OCIO config changed in update
- Transform paths changed in new version

**Diagnosis:**
1. Compare OCIO configs before and after update
2. Check color space assignments in grade
3. Verify transform names in node graphs

**Prevention:**
- Lock OCIO config version for project duration
- Archive OCIO config with project
- Test software updates in non-critical environments first
- Document software and ACES versions in project notes

**Resolution:**
1. Restore previous OCIO config
2. Re-assign color spaces if needed
3. Verify grade appearance
4. Re-render if necessary

### 5.4.3.2 Transform Chain Errors

**Symptom: Incorrect Colors After Applying RRT and ODT**

**Cause:**
- Applying RRT+ODT in wrong order (ODT before RRT)
- Skipping RRT and applying ODT directly to scene-referred data
- Applying RRT twice in the transform chain
- Using ACES 1.x RRT+ODT with ACES 2.0 workflow (or vice versa)

**Diagnosis:**
1. Examine the complete transform chain in the node graph
2. Check for duplicate transforms
3. Verify transform order
4. Confirm transform versions match intended ACES version

**Prevention:**
- Use OCIO roles instead of hard-coded transforms where possible
- Label transform nodes clearly
- Use templates with correct transform chains
- Test transforms on known-good test footage

**Resolution:**
1. Correct the transform chain order
2. Remove duplicate transforms
3. Ensure correct versions of RRT and ODT
4. Re-grade if necessary (changing the rendering significantly affects appearance)

**Symptom: "Double Rendering" Appearance**

**Cause:**
- Applying ACES 1.x RRT+ODT, then re-applying ACES 2.0 transforms
- Rendering to a display color space, then treating it as scene-referred and applying RRT+ODT again
- Incorrect color space assignments causing transforms to be applied twice

**Diagnosis:**
1. Check for multiple RRT applications in node graph
2. Verify color space assignments at each node
3. Look for output-referred data being treated as scene-referred

**Prevention:**
- Understand the data state (scene-referred vs output-referred) at each point in the pipeline
- Use color space names and roles correctly in OCIO
- Test with simple known footage to verify transform behavior

**Resolution:**
1. Remove duplicate RRT applications
2. Correct color space assignments
3. Re-grade from the correct starting point
4. Verify final appearance matches expectations

### 5.4.3.3 HDR and SDR Rendering Issues

**Symptom: HDR Grade Doesn't Translate to SDR**

**Cause:**
- Using ACES 2.0 RRT for HDR but ACES 1.x RRT+ODT for SDR
- Inconsistent creative intent between HDR and SDR grades
- SDR downconversion not optimized for ACES 2.0

**Diagnosis:**
1. Check transform versions used for HDR and SDR
2. Compare HDR and SDR grades side by side
3. Verify SDR ODT is appropriate for target display

**Prevention:**
- Grade HDR first, then derive SDR using appropriate ODT
- Use ACES 2.0 transforms for both HDR and SDR
- Test SDR downconversion workflow before final delivery
- Consider separate HDR and SDR grades if creative intent differs significantly

**Resolution:**
1. Re-apply ACES 2.0 RRT for HDR
2. Use ACES 2.0 SDR ODT for downconversion
3. Make separate creative adjustments for SDR if needed
4. Re-render SDR deliverables

**Symptom: HDR Highlights Appear Wrong**

**Cause:**
- Using ACES 1.x RRT+ODT for HDR (limited HDR support)
- Incorrect ODT for target HDR display
- Display not calibrated to target HDR standard

**Diagnosis:**
1. Verify using ACES 2.0 HDR ODT
2. Check ODT matches target display (PQ 1000, 2000, 4000 nits, HLG, etc.)
3. Verify display calibration

**Prevention:**
- Use ACES 2.0 HDR ODTs
- Select correct ODT for target display
- Calibrate displays to target HDR standard
- Use reference displays for critical evaluation

**Resolution:**
1. Apply correct ACES 2.0 HDR ODT
2. Adjust grade for HDR highlight appearance
3. Re-render HDR deliverable
4. Verify on calibrated reference display

### 5.4.3.4 Backward Compatibility Issues

**Symptom: Cannot Open Older ACES Project in New Software**

**Cause:**

**Resolution:**

2. Update project to reference correct config
3. Migrate project to ACES 2.0 if desired (with re-grading as needed)
4. Test thoroughly after migration

**Symptom: Deliverables Rejected Due to Wrong ACES Version**

**Cause:**

- Deliverable specs not clear about ACES version
- QC facility checks for specific ACES version

**Diagnosis:**
1. Review deliverable specifications
2. Check with client or QC facility about ACES version requirements
3. Verify which ACES version was used for grading and rendering

**Prevention:**
- Clarify ACES version in deliverable specs upfront
- Confirm ACES version with client before starting grade
- Document ACES version in all paperwork and metadata
- Include ACES version information in file naming where appropriate

**Resolution:**
1. If ACES 1.x required, re-grade using ACES 1.x transforms
2. Re-render deliverables from corrected grade
3. Re-submit for QC
4. Update project documentation for future reference

### 5.4.3.5 Performance and Rendering Issues

**Symptom: Slow Rendering with ACES 2.0 Transforms**

**Cause:**
- ACES 2.0 transforms are more computationally complex (CAM integration)
- Software not optimized for new transforms
- Insufficient hardware resources for transform calculations

**Diagnosis:**
1. Compare render times with ACES 1.x vs ACES 2.0
2. Check system resource usage during rendering
3. Test on different hardware configurations

**Prevention:**
- Use appropriate hardware for ACES 2.0 workflow
- Optimize software settings for transform performance
- Cache rendered results where possible
- Use proxy resolutions for interactive work

**Resolution:**
1. Optimize transform caching in software
2. Use GPU acceleration if available
3. Consider pre-rendering RRT for interactive work
4. Upgrade hardware if necessary

**Symptom: Visual Artifacts in Transformed Images**

**Cause:**
- Transform implementation bugs in software
- Numerical precision issues in transform calculations
- Incorrect transform file formats or versions

**Diagnosis:**
1. Check for patterns in artifacts (specific colors, luminance levels, etc.)
2. Test with simple known footage (color charts, gradients)
3. Compare results across different software tools
4. Verify transform file integrity

**Prevention:**
- Use official ACES 2.0 transforms from Academy sources
- Keep software updated for bug fixes
- Test transforms thoroughly before critical use
- Report bugs to software vendors and ACES project

**Resolution:**
1. Update to latest software version
2. Re-download transform files from official sources
3. Report persistent issues to software vendor
4. Use alternative software if issue is tool-specific

## 5.4.4 ACES 2.0 Mini Glossary

**ACES 2.0**: The second generation of the Academy Color Encoding System, featuring decoupled RRT and ODT architecture, improved HDR support, and integration of Color Appearance Modeling (CAM). As of 2024-2025, ACES 2.0 is under active development and early adoption, representing the current evolution of the ACES standard for digital cinema color management.

**CAM (Color Appearance Modeling)**: Mathematical models that predict how colors appear to human observers under varying viewing conditions. ACES 2.0 incorporates CAM to improve perceptual uniformity, highlight rolloff, shadow detail, and saturation relationships, resulting in more natural color appearance compared to ACES 1.x.

**IDT (Input Device Transform)**: A transform that converts camera-specific RGB values to the ACES 2065-1 scene-referred color space. ACES 2.0 introduces updated IDTs for modern cameras (Arri Alexa 35, RED V-Raptor, Sony Venice 2, etc.), improved metadata handling, and better RAW processing integration.

**OCIO 2.0 (OpenColorIO 2.0)**: The version of OpenColorIO required for ACES 2.0, featuring updated configuration structures that support the decoupled RRT and ODT architecture. OCIO 2.0 configs define separate roles for rendering (RRT) and output (ODT), reflect new naming conventions, and clearly specify ACES version information.

**ODT (Output Device Transform)**: A transform that maps output-referred image data to a specific display device's color space and transfer function. In ACES 2.0, ODTs are decoupled from the RRT, handling only display-specific mapping for various targets including HDR (PQ, HLG) and SDR (Rec.709, P3, sRGB) displays.

**RRT (Reference Rendering Transform)**: A standardized creative rendering transform that converts scene-referred ACES 2065-1 data to output-referred display-ready values. In ACES 2.0, the RRT is standalone (not coupled with ODT as in ACES 1.x), incorporates Color Appearance Modeling for improved perceptual uniformity, and serves as a creative starting point resembling film print emulation.

**Backward Compatibility**: The ability of ACES 2.0 to work with ACES 1.x projects and data. While ACES 2065-1 scene-referred data remains compatible, the significant changes in RRT and ODT architecture mean that grades created with ACES 1.x will not match when re-rendered with ACES 2.0 transforms. Maintaining separate ACES 1.x and 2.0 OCIO configs and documenting ACES version are essential for managing compatibility during the transition period.
