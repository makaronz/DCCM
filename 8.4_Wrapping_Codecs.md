# 8.4 Wrapping Codecs (Container Formats)

## Theory

### Container vs Codec

A [container] (or wrapper) is the file format that holds video, audio, and metadata, distinct from the codec that compresses the data:

**Container Responsibilities:**
- Organize multiple streams (video, audio, subtitles)
- Store metadata (timecode, reel names, camera info)
- Define file structure and interoperability
- Enable seeking and random access
- Support edit decision lists and metadata

**Codec Responsibilities:**
- Compress and decompress video data
- Define quality and file size
- Determine compatibility requirements
- Handle color and image data

**Analogy:**
- Codec = Language (English, Spanish, French)
- Container = Book format (hardcover, paperback, e-book)
- Content can be in any language, presented in various formats

### Metadata and Editability

**Metadata Types:**

*Technical Metadata:*
- Codec information
- Resolution, frame rate, aspect ratio
- Bit depth and color space
- Audio sample rate and bit depth

*Production Metadata:*
- Timecode
- Reel/clip names
- Scene/take information
- Camera settings (ISO, white balance, lens)

*User Metadata:*
- Custom comments
- Tags and ratings
- Location data (GPS)
- Copyright information

**[Editability]** refers to how well a container supports professional editing workflows:

*High Editability:*
- Frame-accurate seeking
- Easy metadata access
- Streamable without full decode
- Sample-accurate audio sync

*Low Editability:*
- Requires full decode for editing
- Limited metadata access
- Difficult frame accuracy
- Proprietary formats

### Container Evolution

**Historical Context:**
- Early digital video: AVI (Microsoft), QuickTime (Apple)
- Broadcast: MXF (Material Exchange Format)
- Consumer: MP4 (MPEG-4 Part 14)
- Modern: Cloud-optimized formats (CMAF)

**Current Trends:**
- IP-based production (SMPTE ST 2110)
- Cloud-native workflows
- IMF (Interoperable Master Format)
- HDR metadata support

## Practice

### Container Selection

**Professional Production Containers:**

*MXF (Material Exchange Format):*
- Broadcast and cinema standard
- Supports multiple codecs (ProRes, DNxHD, DCP)
- Excellent metadata support
- Complex but robust
- Multiple operational patterns (OP1a, OP-Atom)
- Best for: Broadcast, archival, interchange

*MOV (QuickTime Movie):*
- Apple standard, widely adopted
- Supports most codecs (ProRes, DNxHR, H.264)
- Good metadata support
- Flexible and well-supported
- Best for: Post-production, editing, mastering

**Consumer/Distribution Containers:**

*MP4 (MPEG-4 Part 14):*
- Ubiquitous web format
- H.264/H.265 typically
- Limited metadata compared to MXF/MOV
- Highly compatible
- Best for: Web delivery, streaming, mobile

**Proprietary Containers:**

*R3D (REDCODE RAW):*
- RED RAW format
- Optimized for RED workflow
- Extensive metadata
- Requires RED software or plugins
- Best for: RED camera workflows

*ARI (ARRIRAW):*
- ARRI RAW format
- Uncompressed or lightly compressed
- Professional workflows
- Best for: ARRI camera workflows

### Metadata Preservation

**Critical Metadata Throughout Pipeline:**

1. **Camera Original**
   - Complete camera metadata
   - Timecode and reel names
   - Scene/take information
   - Do not modify original files

2. **Edit Proxy**
   - Preserve essential metadata (timecode, reel)
   - Add edit-specific metadata (markers, comments)
   - Link back to camera original

3. **Grading Master**
   - Maintain all original metadata
   - Add grading decisions
   - Include LUT/CDL associations

4. **Distribution**
   - Include delivery metadata (aspect ratio, color space)
   - Add platform-specific requirements
   - Preserve technical metadata

**Metadata Preservation Strategies:**
- Use XML/EDL for edit decisions
- Maintain sidecar files when re-wrapping
- Test metadata transfer between systems
- Document any metadata transformations
- Keep original camera files untouched

### Workflow Considerations

**Editing Workflows:**

*Proxy Workflow:*
- Camera original → Edit proxy (lighter codec)
- Edit in proxy → Conform back to original
- Metadata linking critical
- Common for large projects

*Native Editing:*
- Edit camera original directly
- No conform step
- Requires fast storage and CPU
- Increasingly common with modern hardware

*Transcoded Workflow:*
- Transcode to intermediate codec (ProRes/DNxHR)
- Edit intermediate → Keep original for conform
- Balance of performance and quality

**Archive Considerations:**

*Format Longevity:*
- MXF: Best for long-term archival (standardized)
- MOV: Good, but Apple-dependent
- MP4: Excellent compatibility
- Proprietary: Risky (R3D, ARI)

*Archival Strategies:*
- Keep camera original untouched
- Archive in open format (MXF, DPX)
- Include metadata separately (XML reports)
- Multiple copies on different media
- Regular migration to new media (every 5-7 years)

**Delivery Requirements:**

*Broadcast:*
- MXF typically required
- Specific codec (XDCAM, ProRes)
- Loudness standards (EBU R128)
- Closed captions and subtitles

*Cinema (DCP):*
- MXF wrapper (JPEG 2000 codec)
- Specific folder structure
- Resolution and frame rate constraints
- No audio level standardization

*Web (Netflix, Amazon, YouTube):*
- MP4 typically
- H.264/H.265 codec
- HDR metadata requirements
- Specific bitrate requirements

## Failure Modes

### Wrong Container

**Symptoms:**
- File won't play on target system
- Software rejects file
- Metadata missing or corrupted
- Audio sync issues

**Causes:**
- Used consumer container for broadcast delivery
- Used proprietary container without proper software
- Mismatched container and codec combinations
- Incompatible wrapper for target platform

**Mitigation:**
- Research delivery specifications before production
- Test file on target system before final delivery
- Have transcoding options available
- Use standard containers for interoperability
- Keep camera masters in original format

### Lost Metadata

**Symptoms:**
- Timecode missing or incorrect
- Reel names reset to default
- Camera settings lost
- Cannot conform back to camera original

**Causes:**
- Re-wrapping without metadata preservation
- Wrong software or settings
- Incompatible container formats
- User error (overwriting original files)

**Mitigation:**
- Never modify camera originals
- Use professional software for transcodes
- Verify metadata after any file operations
- Keep metadata reports
- Test workflow before critical work

### Compatibility Issues

**Symptoms:**
- Software cannot open file
- Hardware player rejects file
- Partial playback or glitches
- Missing features (subtitles, multiple audio tracks)

**Causes:**
- Unsupported container format
- Incompatible codec/container combination
- Old software without modern format support
- Platform-specific formats

**Mitigation:**
- Check compatibility before starting project
- Use widely-supported formats when possible
- Keep multiple software options available
- Have transcoding backup plan
- Test on target systems early

## Mini Glossary

- **[Container]**: File format that holds video, audio, and metadata data streams, also called wrapper, distinct from codec.

- **[MOV]**: QuickTime Movie container format developed by Apple, widely supported, used in professional video production.

- **[MXF]**: Material Exchange Format, professional container standardized by SMPTE, used in broadcast and cinema workflows.

- **[MP4]**: MPEG-4 Part 14 container format, ubiquitous for web video and streaming, highly compatible.

- **[Metadata]**: Data embedded in or accompanying video files describing technical parameters, production information, and user annotations.

- **[Wrapper]**: Alternative term for container format, holds encoded video/audio and metadata in organized file structure.

- **[Editability]**: Degree to which container format supports professional editing workflows (frame accuracy, seeking, metadata access).

- **[Timecode]**: Frame-accurate timing information embedded in video files, critical for synchronization and editing workflows.

- **[OP1a]**: MXF operational pattern for single program, self-contained file, commonly used for delivery and mastering.

- **[OP-Atom]**: MXF operational pattern for single essence per file, commonly used in Avid workflows.
