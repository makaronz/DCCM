## Theory

### Perceptually Uniform Color Spaces

Traditional color spaces like CIE XYZ and RGB are **not perceptually uniform**—equal numerical distances in these spaces do not correspond to equal perceptual differences. [Perceptual uniformity] [Property of color space where Euclidean distance correlates with perceived color difference] is essential for accurate color evaluation, gamut mapping, and quality metrics.

**CIE LAB (1976) Limitations:**
- Not truly perceptually uniform
- MacAdam ellipses vary in size across gamut
- Poor performance in high-chroma regions (especially blue-purple)
- Inaccurate for HDR and wide-gamut content
- Developed for SDR reflecting surfaces, not emissive displays

**Modern Alternatives:**
```
Perceptual Uniformity Evolution:
1976: CIE LAB (approximate uniformity)
2000: IPT (improved uniformity)
2016: JzAzBz (HDR-optimized, uniform)
2020: ICtCp (constant luminance, efficient)
2022: zcd (uniform and simple)
```

### JzAzBz: HDR Perceptual Uniformity

[JzAzBz] [Perceptually uniform color space designed for HDR and wide-gamut imaging, optimized for human vision] was developed by Safdar, Lai, and Yang (2017) to address limitations of CIE LAB for modern HDR workflows.

**Theoretical Foundation:**
- Based on human vision physiology
- Optimized for peak luminance of 10,000 nits
- Maintains perceptual uniformity across full HDR range
- Constant hue lines align with perception
- Better correlation with perceived color difference than CIE LAB

**Mathematical Construction:**

```
JzAzBz Derivation Pipeline:
XYZ → → Spectral sharpening → → PQ encoding → → Hybrid log → → JzAzBz

Step 1: Spectral Sharpening Matrix (M):
X' = 1.0 × X + 0.0 × Y + 0.0 × Z
Y' = 0.0 × X + 1.0 × Y + 0.0 × Z
Z' = 0.0 × X + 0.0 × Z + 1.0 × Z

Step 2: PQ Encoding (SMPTE ST 2084):
L' = PQ(Y') where Y' is luminance in nits

Step 3: Hybrid Log Processing:
Iz = (409 × J') / 297 + 61 × (J')^2 / 900,000 + 2
az = (409 × a') / 297 + 61 × (a')^2 / 900,000 + 2
bz = (409 × b') / 297 + 61 × (b')^2 / 900,000 + 2

Step 4: Final JzAzBz:
Jz = (Iz - 2) / 13
Az = az / 13
Bz = bz / 13
```

**Key Properties:**
1. **Perceptual Uniformity:**
   - ΔE JzAzBz of 1.0 = just-noticeable difference (JND)
   - Uniform across entire HDR range
   - Better than CIE LAB by factor of 2-4×

2. **Hue Linearity:**
   - Constant hue lines are straight
   - Hue angle correlates with perceived hue
   - Critical for color grading decisions

3. **Luminance Independence:**
   - Chromaticity differences independent of lightness
   - Essential for HDR grading
   - Accurate evaluation across brightness levels

**Applications in Color Management:**
- HDR quality metrics (ΔE JzAzBz < 2.0 = imperceptible)
- Gamut boundary analysis for HDR
- Tone mapping quality assessment
- Color difference evaluation for HDR
- Perceptual quantization optimization

### ICtCp: Constant Luminance Color Space

[ICtCp] [Constant-luminance color space developed by Dolby for HDR video, offering improved compression efficiency and color processing] was standardized in SMPTE ST 2084-2 (2022) as part of the IPT-PQ system.

**Theoretical Foundation:**
- Developed from IPT color space (Ebner and Fairchild, 1998)
- Modified for PQ EOTF compatibility
- Maintains constant luminance (I ≈ Y)
- Optimized for video signal processing
- Better compression than YCbCr for HDR

**Mathematical Construction:**

```
ICtCp from Rec.2020 RGB:

Step 1: RGB to LMS (using Rec.2020 primaries):
┌          ┐   ┌                           ┐   ┌      ┐
│ L'       │   │ 1688  2146   832  (1/4096)│ │ R'   │
│ M'       │ = │ 683   2951  462  (1/4096)│ │ G'   │
│ S'       │   │ 99    309   3688 (1/4096)│ │ B'   │
└          ┘   └                           ┘   └      ┘

Step 2: Apply PQ EOTF (invert for linear):
L = PQ_inverse(L')
M = PQ_inverse(M')
S = PQ_inverse(S')

Step 3: LMS to IPT:
┌       ┐   ┌                          ┐   ┌       ┐
│ I     │   │ 0.4000   0.4000   0.2000 │ │ L     │
│ C     │ = │ 4.4550  -4.4550   0.0000 │ │ M     │
│ Cp    │   │ 0.8056   0.8056  -1.6112 │ │ S     │
└       ┘   └                          ┘   └       ┘

Note: I represents luminance (≈Y)
      C represents red-green opposition
      Cp represents blue-yellow opposition

Inverse Transform (ICtCp to RGB):
Reverse the process: IPT → LMS → PQ → RGB
```

**Key Properties:**
1. **Constant Luminance:**
   - I channel ≈ Y (luminance)
   - Chroma (C, Cp) independent of luminance
   - Critical for HDR processing
   - Enables independent chroma/luma adjustments

2. **Compression Efficiency:**
   - 10-15% better bitrate than YCbCr for HDR
   - Less visible artifacts at same bitrate
   - Better quality for streaming HDR content
   - Adopted for Dolby Vision and HDR10+

3. **Color Processing Advantages:**
   - Color saturation adjustments don't affect brightness
   - Hue rotations maintain luminance
   - Simplifies chroma subsampling decisions
   - Better for color grading operations

**Applications in Color Management:**
- HDR video codec optimization
- Streaming HDR content delivery
- Color grading operations in HDR
- Chroma subsampling for HDR
- Quality metrics for HDR video

### CAT16: Chromatic Adaptation Transform

[CAT16] [Modern chromatic adaptation transform developed for CIECAM16, providing accurate white point conversion] represents the current state-of-the-art for predicting color appearance under different illumination conditions.

**Theoretical Foundation:**
- Improves upon Bradford transform (used in CIE CAM97s)
- Better handles saturation changes
- More accurate for blue region
- Compatible with CIECAM16 color appearance model
- Reversibility (forward and inverse transforms)

**Mathematical Construction:**

```
CAT16 Transform (Adaptation from D65 to D50):

Step 1: Convert XYZ to Sharp RGB primaries:
┌       ┐   ┌                         ┐   ┌     ┐
│ R     │   │  1.05118   0.00000  -0.05118 │ │ X   │
│ G     │ = │  0.00000   1.00000   0.00000 │ │ Y   │
│ B     │   │  0.00000   0.00000   1.00000 │ │ Z   │
└       ┘   └                         ┘   └     ┘

Step 2: Calculate adaptation matrix D:
For incomplete adaptation (typical for displays):
D = F × [1 - (1/3.6) × exp((-5 × LA - 5)/10)]

Where:
F = 1.0 (hard-copy/reflective)
F = 0.8 (typical display viewing)
LA = adapting field luminance in cd/m²

Step 3: Compute degree of adaptation for each channel:
D_RGB = D × (Y_source / Y_reference)

Step 4: Apply chromatic adaptation:
R_adapted = (R_source × D_R + (1 - D_R) × R_reference)
G_adapted = (G_source × D_G + (1 - D_G) × G_reference)
B_adapted = (B_source × D_B + (1 - D_B) × B_reference)

Step 5: Convert back to XYZ:
┌       ┐   ┌                         ┐   ┌         ┐
│ X'    │   │  0.95132   0.00000   0.04868 │ │ R_adapt │
│ Y'    │ = │  0.00000   1.00000   0.00000 │ │ G_adapt │
│ Z'    │   │  0.00000   0.00000   1.00000 │ │ B_adapt │
└       ┘   └                         ┘   └         ┘
```

**Comparison to Bradford Transform:**

| Property | Bradford (1994) | CAT16 (2016) |
|----------|-----------------|--------------|
| Blue accuracy | Moderate | Improved |
| Saturation prediction | Overestimates | More accurate |
| Inverse transform | Lossy | Reversible |
| HDR compatibility | Limited | Full support |
| Viewing condition dependency | Fixed | Adaptive |

**Applications in Color Management:**
- White point conversion (D50 ↔ D65 ↔ D93)
- Display characterization and profiling
- Color appearance modeling
- Cross-media color reproduction
- Illuminant metameric prediction

### Tone Mapping Operators

[Tone mapping] [Process of mapping high dynamic range content to lower dynamic range displays while preserving perceived image quality] is essential for HDR production workflows.

**Classification of Tone Mapping Operators:**

1. **Global Operators:**
   - Apply same curve to all pixels
   - Fast computation
   - May cause local contrast loss
   - Examples: Reinhard, Drago, Ward

2. **Local/Adaptive Operators:**
   - Adapt to local image content
   - Better preservation of details
   - Computationally expensive
   - Examples: Durand, Fattal, Mantiuk

3. **Perceptually-Based Operators:**
   - Model human vision system
   - Maintain perceptual quality
   - Complex implementation
   - Examples: Patterson, Tumblin

**Modern Tone Mapping Equations:**

```
1. Reinhard Tone Mapping (Global):
L_out = (L_in × (1 + L_in / L_white²)) / (1 + L_in)

Where:
L_in = input HDR luminance (0-10,000 nits)
L_white = white point adaptation parameter
L_out = output SDR luminance (0-100 nits)

2. ITU-R BT.2390 EETF (for HDR to SDR):
EETF = {
  (p × EOTF(Y_in)) + (1 - p)           for Y_in < knee_point
  (knee_slope × EOTF(Y_in))^0.25        for Y_in ≥ knee_point
}

Where:
p = 1.07 (SDR gain)
knee_point = 0.65 (transition point)
knee_slope = 3.0 (slope above knee)

3. Hyllgaard Tone Mapping (H.273):
Y_out = {
  3 × Y_in                                     for Y_in < 0.179
  (0.564 × Y_in + 0.096) / (Y_in + 0.264)      for 0.179 ≤ Y_in < 2.2
  1.0 - (0.564 × (1 - Y_in) + 0.096) /         for Y_in ≥ 2.2
        (2 - Y_in + 0.264)
}
```

**Quality Metrics for Tone Mapping:**

```
Tone Mapping Quality Assessment:

1. Perceptual Metrics:
   - HDR-VDP-2: Visible difference prediction
   - ΔE JzAzBz: Color difference in uniform space
   - PU21: Perceptual uniformity metric
   - Target: ΔE < 2.0 (imperceptible)

2. Structural Metrics:
   - SSIM: Structural similarity index
   - MS-SSIM: Multi-scale SSIM
   - VIF: Visual information fidelity
   - Target: >0.95 (high quality)

3. Artifact Detection:
   - Banding: Visible steps in gradients
   - Clipping: Loss of highlight/shadow detail
   - Reversal: Inversion of brightness order
   - False contouring: Mach band effects
   - Target: No visible artifacts
```

import numpy as np

def xyz_to_jzazbz(X, Y, Z):
    """
    Convert CIE XYZ to JzAzBz color space
    Input: XYZ values (normalized to [0,1])
    Output: JzAzBz values
    """
    # Step 1: Apply PQ EOTF (assuming Y is already PQ-encoded)
    # If linear luminance, apply ST 2084 PQ first

    # Step 2: Apply spectral sharpening matrix
    X_prime = 1.0 * X + 0.0 * Y + 0.0 * Z
    Y_prime = 0.0 * X + 1.0 * Y + 0.0 * Z
    Z_prime = 0.0 * X + 0.0 * Y + 1.0 * Z

    # Step 3: Hybrid log processing
    def hybrid_log(v):
        return (409 * v) / 297 + 61 * v**2 / 900000 + 2

    Iz = hybrid_log(Y_prime)
    az = hybrid_log((X_prime - Y_prime) * 1.66)
    bz = hybrid_log((Y_prime - Z_prime) * 0.66)

    # Step 4: Final JzAzBz
    Jz = (Iz - 2) / 13.0
    Az = az / 13.0
    Bz = bz / 13.0

    return Jz, Az, Bz

def delta_e_jzazbz(Jz1, Az1, Bz1, Jz2, Az2, Bz2):
    """
    Calculate ΔE in JzAzBz color space
    Returns perceptual color difference
    """
    dJ = Jz1 - Jz2
    dA = Az1 - Az2
    dB = Bz1 - Bz2

    delta_e = np.sqrt(dJ**2 + dA**2 + dB**2)
    return delta_e

# Quality thresholds for HDR
def evaluate_hdr_quality(delta_e):
    """
    Interpret ΔE JzAzBz values for HDR content
    """
    if delta_e < 1.0:
        return "Imperceptible (Excellent)"
    elif delta_e < 2.0:
        return "Just Noticeable (Good)"
    elif delta_e < 4.0:
        return "Noticeable (Acceptable)"
    elif delta_e < 8.0:
        return "Clearly Visible (Poor)"
    else:
        return "Extremely Visible (Unacceptable)"

# Practical example: Compare HDR to SDR tone mapping
def assess_tone_mapping(hdr_xyz, sdr_xyz):
    """
    Assess quality of HDR to SDR tone mapping
    """
    Jz_hdr, Az_hdr, Bz_hdr = xyz_to_jzazbz(*hdr_xyz)
    Jz_sdr, Az_sdr, Bz_sdr = xyz_to_jzazbz(*sdr_xyz)

    delta_e = delta_e_jzazbz(Jz_hdr, Az_hdr, Bz_hdr,
                             Jz_sdr, Az_sdr, Bz_sdr)

    quality = evaluate_hdr_quality(delta_e)

    return {
        'delta_e': delta_e,
        'quality': quality,
        'Jz_hdr': Jz_hdr, 'Az_hdr': Az_hdr, 'Bz_hdr': Bz_hdr,
        'Jz_sdr': Jz_sdr, 'Az_sdr': Az_sdr, 'Bz_sdr': Bz_sdr
    }
```

import numpy as np

def rgb2020_to_icpctcp(R, G, B):
    """
    Convert Rec.2020 RGB to ICtCp
    Input: RGB values [0,1] (linear or PQ-encoded)
    Output: ICtCp values (I: ~[0,1], Cp/Ct: ~[-0.5,0.5])
    """
    # Step 1: RGB to LMS (Rec.2020 matrix)
    L = (1688*R + 2146*G + 832*B) / 4096
    M = (683*R + 2951*G + 462*B) / 4096
    S = (99*R + 309*G + 3688*B) / 4096

    # Step 2: Apply PQ EOTF (if input is linear)
    # For PQ-encoded input, skip this step
    L_pq = st2084_eotf(L) if is_linear(L) else L
    M_pq = st2084_eotf(M) if is_linear(M) else M
    S_pq = st2084_eotf(S) if is_linear(S) else S

    # Step 3: LMS to IPT (PQ-adapted)
    I = 0.4000*L_pq + 0.4000*M_pq + 0.2000*S_pq
    C = 4.4550*L_pq - 4.4550*M_pq + 0.0000*S_pq
    Cp = 0.8056*L_pq + 0.8056*M_pq - 1.6112*S_pq

    return I, C, Cp

def icpctcp_to_rgb2020(I, C, Cp):
    """
    Convert ICtCp to Rec.2020 RGB
    Inverse transform
    """
    # Step 1: IPT to LMS
    L_pq = 1.0*I + 0.0094*C + 0.1116*Cp
    M_pq = 1.0*I - 0.0094*C + 0.1116*Cp
    S_pq = 1.0*I - 0.0000*C - 0.6172*Cp

    # Step 2: Apply PQ inverse EOTF
    L = st2084_inverse_eotf(L_pq)
    M = st2084_inverse_eotf(M_pq)
    S = st2084_inverse_eotf(S_pq)

    # Step 3: LMS to RGB
    R = (4096/1688) * L
    G = (4096/2951) * M
    B = (4096/3688) * S

    return R, G, B

def compress_icpctp(I, C, Cp, bit_depth=10):
    """
    Optimized bit-depth allocation for ICtCp
    Higher bit-depth for I (luminance), lower for chroma
    """
    # Allocate more bits to I (luminance)
    I_bits = bit_depth  # Full bit-depth
    C_bits = bit_depth - 2  # 2 fewer bits
    Cp_bits = bit_depth - 2  # 2 fewer bits

    # Quantize
    I_q = np.round(I * (2**I_bits - 1))
    C_q = np.round(C * (2**C_bits - 1))
    Cp_q = np.round(Cp * (2**Cp_bits - 1))

    # For 10-bit: I=10 bits, C=8 bits, Cp=8 bits
    # Total: 26 bits vs 30 bits for RGB 10-bit
    # Compression ratio: 1.15×

    return I_q, C_q, Cp_q
```

def subsample_ictpcp(I, C, Cp, subsampling='4:2:0'):
    """
    Chroma subsampling in ICtCp domain
    Better quality than YCbCr for HDR
    """
    height, width = I.shape

    if subsampling == '4:2:0':
        # Halve chroma resolution horizontally and vertically
        C_sub = C[::2, ::2]
        Cp_sub = Cp[::2, ::2]
    elif subsampling == '4:2:2':
        # Halve chroma resolution horizontally only
        C_sub = C[:, ::2]
        Cp_sub = Cp[:, ::2]
    elif subsampling == '4:4:4':
        # No subsampling
        C_sub = C
        Cp_sub = Cp

    return I, C_sub, Cp_sub

def evaluate_subsampling_quality(original_icpctp, subsampled_icpctp):
    """
    Evaluate quality loss from chroma subsampling in ICtCp
    """
    I_orig, C_orig, Cp_orig = original_icpctp
    I_sub, C_sub, Cp_sub = subsampled_icpctp

    # Upsample chroma to original size

    Cp_upsampled = upscale_chroma(Cp_sub, target_shape=Cp_orig.shape)

    # Calculate errors
    delta_I = np.mean(np.abs(I_orig - I_sub))  # Should be ~0

def apply_cat16(color_xyz, source_white, target_white, degree=0.8):
    """
    Apply CAT16 chromatic adaptation transform
    """
    # Convert XYZ to Sharp RGB
    rgb_sharp = xyz_to_sharp_rgb(color_xyz)

    # Calculate adaptation factors

    return xyz_adapted

def hdr_to_sdr_tone_map(hdr_pq, method='bt2390'):
    """
    Convert HDR (PQ-encoded) to SDR using tone mapping
    """
    sdr_frames = []

    for frame in hdr_pq:
        if method == 'bt2390':
            # ITU-R BT.2390 EETF
            sdr = bt2390_tone_map(frame)
        elif method == 'reinhard':
            # Reinhard global tone mapping
            sdr = reinhard_tone_map(frame)
        elif method == 'adaptive':
            # Local adaptive tone mapping
            sdr = adaptive_tone_map(frame)
        elif method == 'hyllgaard':
            # H.273 Hyllgaard
            sdr = hyllgaard_tone_map(frame)

        sdr_frames.append(sdr)

    return np.array(sdr_frames)

def bt2390_tone_map(hdr_pq):
    """
    ITU-R BT.2390 EETF for HDR to SDR conversion
    Industry standard for broadcast
    """
    # Convert PQ to linear
    hdr_linear = pq_to_linear(hdr_pq)

    # Apply BT.2390 EETF
    knee_point = 0.65
    knee_slope = 3.0
    sdr_gain = 1.07

    # Below knee point: linear scaling
    mask_below = hdr_linear < knee_point
    sdr_below = sdr_gain * hdr_linear[mask_below]

    # Above knee point: power function
    mask_above = hdr_linear >= knee_point
    sdr_above = knee_slope * np.power(hdr_linear[mask_above], 0.25)

    # Combine
    sdr_linear = np.zeros_like(hdr_linear)
    sdr_linear[mask_below] = sdr_below
    sdr_linear[mask_above] = sdr_above

    # Clip to SDR range
    sdr_linear = np.clip(sdr_linear, 0, 1)

    return sdr_linear

    hdr1000_pq = linear_to_pq(linear_1000)

## Failure Modes

### Wrong Color Space Selection

Selecting inappropriate color spaces for specific tasks leads to significant quality degradation.

**Failure Mode 1: Using CIE LAB for HDR Evaluation**

**Symptoms:**
- Inaccurate color difference measurements
- Poor correlation with perceptual differences
- Overestimation of differences in bright regions
- Underestimation of differences in dark regions
- Inconsistent quality metrics

**Causes:**
- CIE LAB designed for SDR reflecting surfaces
- Not optimized for high luminance levels
- Non-uniform perceptual spacing for HDR
- Developed for 0-100 cd/m², not 0-10,000 nits

**Prevention:**
```
Color Space Selection Guide:
HDR Analysis (100-10,000 nits):
✅ Use: JzAzBz
❌ Avoid: CIE LAB

HDR Video Processing:
✅ Use: ICtCp
❌ Avoid: YCbCr (better for SDR)

Wide Gamut Evaluation:
✅ Use: JzAzBz or IPT
❌ Avoid: CIE LAB (non-uniform in blue-purple)

Cross-White-Point Adaptation:
✅ Use: CAT16
❌ Avoid: Bradford (less accurate)

Tone Mapping Quality:
✅ Use: ΔE JzAzBz
❌ Avoid: ΔE CIE LAB (inaccurate)
```

**Detection:**
- Quality metrics don't correlate with visual assessment
- Unexpected color difference values
- Inconsistent results across luminance levels
- Poor gamut boundary analysis

**Recovery:**
1. Identify inappropriate color space usage
2. Reconvert data to appropriate color space
3. Recalculate metrics and analysis
4. Update documentation and procedures
5. Train team on proper color space selection

**Failure Mode 2: Using YCbCr for HDR Color Processing**

**Symptoms:**
- Luminance shifts when adjusting saturation
- Color banding in saturated regions
- Poor compression efficiency for HDR
- Inaccurate color grading results

**Causes:**

- Chroma and luma coupling at high brightness
- Developed for SDR gamma encoding
- Not optimized for PQ/HLG

**Prevention:**

Video Compression:

Quality Metrics:

## Mini Glossary

**JzAzBz**
Perceptually uniform color space designed for HDR and wide-gamut imaging. Developed in 2016, optimized for human vision across 0-10,000 nits. Provides uniform perceptual spacing where ΔE of 1.0 = just-noticeable difference. Superior to CIE LAB for HDR quality assessment, gamut boundary analysis, and color difference evaluation.

**ICtCp**
Constant-luminance color space developed by Dolby for HDR video processing. Standardized in SMPTE ST 2084-2 (2022). Maintains constant luminance (I ≈ Y) enabling independent chroma and luma processing. Offers 10-15% better compression efficiency than YCbCr for HDR. Used for HDR video codecs, streaming optimization, and color grading operations.

**CAT16**
Modern chromatic adaptation transform developed for CIECAM16 color appearance model. Provides accurate white point conversion between different illuminants (e.g., D50 to D65). Improves upon Bradford transform with better accuracy in blue region and reversibility. Essential for cross-media color reproduction, display characterization, and color appearance prediction.

**Perceptual Uniformity**
Property of color space where Euclidean distance correlates directly with perceived color difference. In perceptually uniform spaces, equal numerical distances produce equal perceptual differences across the entire gamut. Essential for accurate color evaluation, gamut mapping, and quality metrics.

**Constant Luminance**
Property of color representation where luminance (brightness) information is separated from and independent of chroma (color) information. In constant-luminance spaces, adjusting saturation doesn't change brightness. Critical for HDR processing and color grading operations.

**Tone Mapping**
Process of converting high dynamic range content to lower dynamic range while preserving perceived image quality and important details. Essential for HDR to SDR conversion, display adaptation, and cross-standard delivery. Various operators: global (Reinhard), adaptive (Durand), perceptual (Patterson), standard (BT.2390, Hyllgaard).

**Chromatic Adaptation**
Human visual system's ability to adjust perception of colors under different illumination conditions. Chromatic adaptation transforms model this process mathematically, enabling prediction of color appearance when changing white points (e.g., viewing same print under D50 and D65 illumination).

**ΔE (Delta E)**
Metric quantifying color difference between two samples. Values: <1.0 = imperceptible, 1-2 = just noticeable, 2-4 = noticeable, >4 = clearly visible. Accuracy depends on color space: ΔE in JzAzBz more accurate than ΔE in CIE LAB for HDR content.

**Gamut Boundary**
Surface enclosing all reproducible colors in a color space or device. Visualized in 2D as chromaticity diagram or 3D as volume. Gamut boundary analysis essential for color management, gamut mapping, and quality assessment.

**PQ (Perceptual Quantization)**
Transfer function defined in SMPTE ST 2084 for HDR video. Optimized for human perception across 0-10,000 nits. Uses non-linear encoding to allocate more code values to perceptually important brightness ranges. Foundation for HDR10, HDR10+, and Dolby Vision.

**Hybrid Log**
Logarithmic encoding combining advantages of log and power functions. Used in JzAzBz construction and ARRI Log C4. Provides smooth response in shadows and highlights. Critical for perceptual uniformity in HDR imaging.

**LMS Cone Space**
Color space based on human vision's Long (L), Medium (M), and Short (S) wavelength cone responses. Fundamental to color appearance modeling and chromatic adaptation transforms. Basis for modern color science including CAT16.

**IPT Color Space**
Perceptually uniform color space developed by Ebner and Fairchild (1998). Foundation for ICtCp. Provides better hue linearity than CIE LAB. Used as intermediate step in modern color space constructions.

**White Point**
Chromaticity coordinates defining the "white" color in a color space or display. Common standards: D65 (6504K, daylight), D50 (5003K, print viewing), D93 (9300K, old monitors). Critical for color appearance and cross-device consistency.

**Color Appearance Model**
Mathematical model predicting color appearance under varying viewing conditions (illumination, surround, luminance). Examples: CIECAM02, CIECAM16. Used for cross-media color reproduction and appearance matching.

**Dynamic Range**
Ratio between brightest and darkest reproducible signals. SDR: ~100:1 (2-3 stops), HDR: 1,000,000:1 (20 stops). Expressed in stops (log₂) or nits (cd/m² for displays). Critical for image quality and HDR workflows.

**Bit Depth**
Number of bits used to represent each color channel. 8-bit: 256 levels (SDR consumer), 10-bit: 1024 levels (professional SDR), 12-bit: 4096 levels (HDR master). Higher bit depth reduces banding and enables smoother gradients.

**Chroma Subsampling**
Reducing color resolution by sampling chroma channels at lower resolution than luma. Notation: J:a:b (J: horizontal reference, a: chroma horizontal samples, b: chroma vertical samples). Common: 4:2:0 (half resolution), 4:2:2 (half horizontal), 4:4:4 (full resolution).

**Color Difference**
Quantitative measure of perceptual difference between two colors. Calculated as Euclidean distance in perceptually uniform color space (JzAzBz, CIE LAB). Used for quality metrics, gamut mapping evaluation, and color tolerance specification.

**Just-Noticeable Difference (JND)**
Smallest color difference perceptible to human observer under defined viewing conditions. In JzAzBz, ΔE = 1.0 ≈ JND. Critical for setting quality thresholds and compression parameters.

**Gamut Mapping**
Process of converting colors from source to destination gamut while preserving perceptual attributes. Strategies: clip, perceptual, relative colorimetric, saturation. Essential for cross-device reproduction and HDR to SDR conversion.

**Viewing Conditions**
Environmental factors affecting color perception: illuminant (spectral power distribution), surround luminance, adaptation field, viewing angle. Must be standardized for consistent color evaluation (ITU-R BT.2035 for reference viewing).

**Luminance**
Photometric measure of light intensity emitted/reflected from surface, measured in candelas per square meter (cd/m² or nits). Distinct from brightness (perceived) and lightness (relative). Critical for HDR and display calibration.

**Radiance**
Radiometric measure of light power per unit solid angle, measured in watts per steradian per square meter (W·sr⁻¹·m⁻²). Physical quantity independent of human vision, converted to luminance using photometric curve.

**EOTF (Electro-Optical Transfer Function)**
Conversion from electrical signal to display light output. For HDR: PQ EOTF (SMPTE ST 2084) or HLG OOTF. Defines relationship between code values and displayed luminance.

**OOTF (Opto-Optical Transfer Function)**
Overall transfer function including both signal processing and display characteristics. For HLG: OOTF varies with display peak luminance, unlike fixed PQ EOTF. Critical for HDR reference rendering.

**Color Volume**
3D color space defined by chromaticity (gamut) and luminance (dynamic range). For HDR: specifies both color gamut (e.g., Rec.2020) and peak luminance (e.g., 1000 nits). Measured in distinct colors: SDR Rec.709 @ 100 nits ≈ 1 million colors, HDR Rec.2020 @ 1000 nits ≈ 1 billion colors.

### Multi-Primary Displays — Six-Primary Projectors and Rec. 2020 Coverage

Multi-primary display technology has advanced significantly since the original content was written:

**CEDIA 2025 Research Sessions:**
- Six-primary laser projectors (RGB + additional cyan, yellow, and/or magenta primaries) have demonstrated **99.8% Rec. 2020 coverage** (theoretical), with commercial implementations achieving **97–99%** in measured conditions.
- These projectors use **multiple laser diode arrays** with independent primaries, allowing the display system to selectively illuminate the primaries that best cover the target color gamut. This is fundamentally different from traditional three-primary (RGB) projectors, which must "mix" all colors from three primaries.
- **Rec. 2020 coverage** is the key metric for cinema HDR. DCI-P3 (the current cinema standard) covers approximately 53% of visible colors; Rec. 2020 covers 76%. The difference is visible in highly saturated colors (deep reds, vivid greens, intense blues) that are common in VFX and animated content.
- **Six-primary projectors** can display colors that are physically impossible for three-primary displays (including OLED, QD-OLED, and traditional laser projectors). This creates a **new class of color management challenges**: how to grade content for a six-primary display when the mastering monitor is only three-primary (e.g., a standard OLED or LCD reference monitor)?

**Color Management Implications for Multi-Primary Displays:**
- **Gamut mapping from Rec. 2020 to DCI-P3** is well understood (described in the original Gamut Mapping section). But **gamut mapping from a six-primary display to a three-primary master monitor** is a new problem: the colorist sees a desaturated version of the image on the mastering monitor, while the final display shows more saturated colors.
- **Solution approaches:**
  1. **Six-primary mastering monitor:** Use a six-primary reference monitor for grading. Currently, these are research/lab prototypes only. Commercial six-primary monitors are not available as of 2026.
  2. **Gamut preview LUT:** Create a custom LUT that maps the six-primary display gamut to the mastering monitor gamut, so the colorist sees an approximation of the final image. This is analogous to the Rec. 2020 → DCI-P3 preview LUT used today, but more complex because the six-primary gamut is not a simple superset of Rec. 2020 (it has different primary chromaticities).
  3. **Soft-clipping with hue preservation:** Use a gamut mapping algorithm that compresses highly saturated colors into the mastering monitor gamut while preserving hue and relative lightness. This is the current best practice, but requires careful validation on the actual six-primary display.
- **Recommendation:** For productions targeting six-primary display venues (e.g., premium cinema installations, high-end exhibitions), arrange a **proofing session** on the actual display before finalizing the grade. Do not rely solely on the mastering monitor.

### Neural Radiance Fields (NeRF) and 3D Gaussian Splatting in VP and Color

**Neural Radiance Fields (NeRF)** and **3D Gaussian Splatting** are neural rendering techniques that have gained significant traction in virtual production and visual effects since 2022:

**NeRF:**
- NeRF represents a 3D scene as a **neural network** (typically a multi-layer perceptron) that maps 3D position (x, y, z) and viewing direction (θ, φ) to color (RGB) and density (σ).
- **Color management challenge:** NeRF is trained on a set of input photographs with **unknown color spaces**. The neural network learns the color mapping from the training data, but there is no explicit color space metadata. If the training images are in different color spaces (e.g., some in sRGB, some in DCI-P3, some in Rec. 2020), the NeRF output will have inconsistent colors.
- **Best practice:** Pre-process all training images to a **common color space** (e.g., ACES2065-1 or Rec. 2020) before training. Use an ICC profile or color space metadata (EXIF, XMP) to identify the source color space, and apply the appropriate transform. If metadata is unavailable, use a color chart (e.g., ColorChecker) in the scene to derive a color transform.
- **HDR NeRF:** Extensions to NeRF support HDR training data (e.g., multiple exposure brackets). The neural network learns to reconstruct the HDR radiance field, which can then be rendered with any tone mapping operator (e.g., PQ, HLG, or ACES RRT + ODT). This is relevant for HDR VP backgrounds and HDR VFX plates.

**3D Gaussian Splatting (3DGS):**
- 3DGS represents a scene as a set of **3D Gaussian blobs** (ellipsoids) with position, covariance, color (spherical harmonics), and opacity. The scene is rendered by "splatting" these Gaussians onto the image plane, which is extremely fast (real-time on consumer GPUs).
- **Relightable Gaussian Splatting (May 2026):** The latest research (May 2026) has demonstrated **relightable Gaussian Splatting** — the ability to change the lighting conditions (e.g., sun position, time of day) of a reconstructed scene in real-time. This is achieved by decomposing the scene into **albedo** (surface color) and **normal/BRDF** (surface reflectance), and applying a new lighting model.
- **Color management implications for VP:**
  - Relightable 3DGS can be used to generate **LED wall content** for virtual production that adapts to the on-set lighting changes. For example, if the key light on set changes position or intensity, the 3DGS background can be relit to match, improving the realism of the in-camera composite.
  - The albedo layer of the 3DGS must be in a **linear, scene-referred color space** (e.g., ACEScg, Rec. 2020 linear) to allow correct relighting. If the albedo is in a display-referred space (e.g., sRGB with gamma), the relighting will be incorrect (colors will shift unnaturally under different lighting).
  - **DIT workflow:** When using 3DGS for VP, verify that the reconstruction pipeline uses a linear color space for the albedo. If the source photographs are in sRGB, they must be linearized (gamma decoded) before training. The spherical harmonics coefficients used for view-dependent color in 3DGS should also be computed in linear space.
- **Denoising and 3DGS:** NeRF and 3DGS can be combined with **AI denoising** (NVIDIA OptiX, Intel Open Image Denoise) to produce clean, noise-free training data from noisy source images. The denoiser must be applied **before color space conversion**, because denoising in a non-linear space (e.g., sRGB) can create color artifacts.

**Production Applications (2026):**
- **Unreal Engine 5.5:** Includes a Gaussian Splatting plug-in (experimental) that allows importing 3DGS scenes as Nanite assets. This enables real-time 3DGS rendering in VP workflows.
- **Unity 6:** Includes a Gaussian Splatting renderer for both real-time and baked lighting scenarios.
- **VP workflows:** 3DGS is increasingly used for **environment scanning** (capturing a real-world location as a 3D scene for VP background use). This is faster than traditional photogrammetry + mesh reconstruction, and produces more realistic results for organic scenes (vegetation, terrain, irregular surfaces).

**DIT Recommendation for 3DGS/NeRF:**
- Always capture training photographs with **raw sensor data** (not JPEG) to preserve maximum color information and avoid display-referred gamma encoding.
- Use a **color chart** (e.g., ColorChecker Classic, ColorChecker Digital SG) in every training photograph to enable color calibration and cross-image consistency.
- Pre-process all training images to a **common linear color space** (ACES2065-1 or Rec. 2020 linear) before training.
- Verify the output of the neural renderer by comparing a rendered frame to a ground-truth photograph of the same viewpoint, using a color difference metric (e.g., ΔE2000 in CIELAB, or JzAzBz distance for HDR).
- For HDR applications, train with **HDR source data** (multiple exposure brackets) and render with the appropriate EOTF (PQ or HLG).
